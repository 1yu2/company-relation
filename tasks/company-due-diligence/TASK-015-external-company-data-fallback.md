| 属性 | 内容 |
| --- | --- |

## 背景

当前企业尽调以广东企业内部只读数据为事实主库，已经覆盖企业基本信息、股东、关系、产品、融资、风险、知识产权和文本证据等领域。但内部数据可能出现以下情况：

- 企业在内部库中没有融资记录；
- 内部记录存在，但时间较旧；
- 某个数据域只有部分字段；
- 企业属于上市公司或公开披露主体，外部公开数据有更及时的补充；
- 内部数据与外部公开信息存在差异，需要并列展示并交给用户判断。

因此需要增加外部数据补数能力。外部数据不能覆盖内部事实，也不能因为外部数据没有结果就断言企业不存在某项事实。

## 目标

建立“内部数据优先、外部来源补数、结果可审计、缺失可解释”的企业尽调外部数据链路：

1. 保留 `investigate_company` 作为企业尽调智能体的统一入口。
2. 通过领域内的外部数据服务统一编排 Provider，不让主智能体直接随机选择数据源。
3. 通过 Tool 执行结构化外部查询，通过 Skill 约束何时补数、如何合并和如何表达来源。
4. 首期支持 AkShare 等公开财经数据作为可选 Provider，优先服务上市公司公开资料、财务、股东、公告和新闻等场景。
5. 为融资信息预留独立 Provider 接口，后续接入已授权的商业企业数据 API、企业/投资机构公告或其他合规来源。
6. 所有外部事实保留来源、发布时间、获取时间、Provider、原始内容摘要和校验状态。
7. 外部查询失败、限流或数据源不可用时，返回可解释的降级状态；所有候选来源均失败时才将任务标记为外部查询失败。

## 核心原则

### 内部事实优先

内部 MySQL 是当前企业尽调的事实主库。外部数据只能作为：

- 内部缺失字段的补充；
- 内部数据过期后的新鲜度参考；
- 内部与外部冲突时的对照证据；
- 内部尚未覆盖的数据域的公开线索。

外部结果不得直接覆盖内部表、修改内部 `eid`、写回广东 MySQL 或改变已确认企业身份。

### 证据先于结论

外部数据必须先转为统一事实和来源对象，再进入答案或报告渲染。LLM 不能直接根据未登记来源的网页摘要生成企业事实。

### 明确缺失语义

“没有查到”只能表示当前数据源和时间窗口内没有查到可验证记录，不得表述为“企业没有融资”“企业不存在风险”等绝对结论。

### Provider 可替换

AkShare 只是首期可选 Provider，不作为融资历史的唯一来源。外部服务需要支持 Provider 健康状态、超时、限流、缓存和版本化，后续可以接入合规的商业 API、公告查询和人工上传证据。

## 范围

### 1. 外部数据统一契约

新增外部企业数据查询请求和响应模型，建议包含以下字段：

```json
{
  "company_ref": {
    "name": "企业标准全称",
    "eid": "仅使用已确认的内部 eid",
    "unified_credit_code": "可选",
    "stock_code": "可选"
  },
  "topics": ["profile", "financing", "financials", "shareholders", "news"],
  "start_date": "2023-01-01",
  "end_date": "2026-08-12",
  "providers": ["akshare", "public_disclosure"],
  "refresh": false
}
```

响应至少包含：

```json
{
  "facts": [],
  "sources": [],
  "coverage": {},
  "missing_topics": [],
  "conflicts": [],
  "provider_status": [],
  "retrieved_at": "2026-08-12T00:00:00Z"
}
```

### 2. Provider 适配层

定义统一 Provider 接口，禁止业务编排代码直接依赖 AkShare 的原始函数和返回字段。首期至少包含：

```text
ExternalCompanyDataProvider
├── AkShareProvider
├── PublicDisclosureProvider（可先提供接口和未配置状态）
└── FinancingProvider（可先提供接口和未配置状态）
```

Provider 需要支持：

- 按企业身份和主题查询；
- 返回统一事实和来源对象；
- 声明支持的数据域；
- 超时、限流、认证失败和上游格式变化的标准错误；
- 健康检查和可用状态；
- 最小必要缓存；
- 不输出密钥、完整请求参数或敏感原始响应到日志。

### 3. AkShare 首期能力

首期只接入能够稳定映射和验证的公开财经数据，不追求覆盖所有 AkShare 接口。优先考虑：

- 上市公司基本资料；
- 上市公司财务报表和财务指标；
- 主要股东或股本变化；
- 上市公司公告；
- 公开财经新闻或重大事件线索。

每个接口必须登记：

- 上游接口名称和版本；
- 输入字段和企业身份映射规则；
- 输出字段映射；
- 业务日期和发布时间字段；
- 来源 URL 或可复核的来源标识；
- 空结果和异常结果的区别。

### 4. 融资信息补数

融资信息单独抽象为 `FinancingProvider`，不把 AkShare 当作非上市企业融资历史的默认来源。查询顺序建议为：

1. 内部 `t_company_finance`；
2. 企业、投资机构、交易所或监管机构公开披露；
3. 已授权商业企业数据 API；
4. 合规的新闻和公告检索；
5. 其他可配置 Provider。

外部融资事件统一映射为轮次、日期、金额、币种、投资方、估值、标题、来源链接、发布时间、获取时间和置信度。外部融资事件默认进入外部证据快照，不直接写回正式融资表。

### 5. 缺口检测与补数策略

为每个调查主题生成数据质量状态：

```text
complete    内部数据满足当前问题所需字段和时间范围
partial     有记录但字段或时间范围不足
missing     当前内部数据没有记录
stale       有记录但超过新鲜度阈值
conflict    内外或多外部来源存在冲突
unsupported 当前内部链路不支持该主题
```

只有 `partial`、`missing`、`stale`、`conflict` 或 `unsupported` 才允许触发外部查询。补数策略必须记录触发原因和使用过的 Provider。

### 6. 证据与报告集成

外部来源复用现有 `Source`、`Evidence`、`Claim Ledger` 和 `DataQuality` 契约，建议使用以下来源标识格式：

```text
external:<provider>:<topic>:<stable-record-key>:<retrieved-date>
```

报告和问答必须区分：

- 内部事实；
- 外部已核验事实；
- 外部单一来源线索；
- 未核验或来源不足的信息；
- 内外部冲突及冲突字段。

### 7. Tool 与 Skill 接入

新增领域 Tool：

```text
query_external_company_data
```

新增或扩展企业尽调 Skill，明确：

- 企业问题先调用内部尽调服务；
- 只有检测到数据缺口才调用外部 Tool；
- 不允许模型猜测 `eid` 或用外部名称覆盖已确认企业；
- 外部事实必须附来源和获取时间；
- 外部无结果不能推导为事实不存在；
- 发生冲突时返回冲突，不由模型静默裁决。

## 不在范围内

- 不修改广东企业 MySQL 源表、内部 `eid` 或内部事实记录。
- 不把 AkShare 做成覆盖全部企业数据的万能接口。
- 不把 AkShare 作为非上市企业融资历史的唯一数据源。
- 不在首期自动把外部数据写入正式融资表、股东表或风险表。
- 不允许普通用户直接输入 Provider 密钥、内部连接信息或调用任意外部 URL。
- 不允许通过搜索摘要、无来源 LLM 内容或单次异常网页结果直接生成确定性企业事实。
- 不在首期新增独立 MCP 服务；仅当多个智能体复用且 Provider 稳定后再拆分。
- 不在本任务中改造企业身份解析、图谱多跳查询或报告输入输出契约。

## 建议实现步骤

1. 冻结外部事实、来源、覆盖状态、Provider 状态和冲突对象契约。
2. 定义 `ExternalCompanyDataProvider`、Provider 注册表和标准错误分类。
3. 实现外部查询服务、缓存、超时、限流、健康状态和脱敏日志。
4. 实现 AkShare 首期 Provider，并为公告/融资 Provider 保留明确的未配置状态。
5. 在现有调查计划中加入主题级缺口检测和外部补数决策，不改变内部查询白名单。
6. 将外部事实转换为现有 `Source`、`Evidence` 和 `Claim Ledger`，接入报告与问答渲染。
7. 新增外部数据 Tool，并通过企业尽调 Skill 控制其使用条件。
8. 增加管理端 Provider 配置、健康检查、缓存清理和查询审计入口；敏感凭据只从服务端配置读取。
9. 完成单元、集成和关键 E2E 回归后，再评估是否拆为平台级 MCP。

## 数据来源与可信度规则

建议默认按以下优先级展示和冲突处理：

1. 内部审计数据；
2. 政府、监管机构、交易所和法院公开披露；
3. 企业或投资机构正式公告；
4. 已授权商业企业数据 API；
5. AkShare 等公开财经聚合数据；
6. 权威媒体；
7. 普通网页检索线索。

来源优先级不能替代事实校验。冲突字段必须保留各来源和日期，不能仅按 Provider 优先级静默覆盖。

## 验收 checklist

- [ ] 外部查询请求和响应契约冻结，支持企业身份、主题、时间范围和 Provider 选择。
- [ ] 内部查询完成后能输出主题级 `complete`、`partial`、`missing`、`stale`、`conflict` 或 `unsupported` 状态。
- [ ] 缺口检测只在允许状态下触发外部查询，并记录触发原因。
- [ ] Provider 接口与 AkShare 适配器解耦，AkShare 原始字段不泄漏到业务层。
- [ ] AkShare 首期至少覆盖一组上市公司公开资料或财务数据，并有真实或录制响应测试。
- [ ] 外部融资 Provider 有统一接口；未配置时返回明确状态，不伪造融资结果。
- [ ] 外部事实携带稳定 `source_id`、来源标识、业务日期、获取时间和校验状态。
- [ ] 外部结果不会写入广东 MySQL，也不会自动覆盖内部事实。
- [ ] 内外部冲突能被识别、保留并在回答/报告中展示。
- [ ] 所有外部确定性结论都能在现有来源索引和 Claim Ledger 中追溯。
- [ ] Provider 超时、限流、认证失败、空结果和上游格式变化有不同错误状态。
- [ ] 外部数据缓存、限流、审计日志和敏感信息脱敏通过测试。
- [ ] 主聊天企业尽调入口、结构化查询、关系查询和报告链路回归通过。
- [ ] 相关单元、集成、E2E、格式化、Lint 和文档检查通过。

## 建议测试范围

### 单元测试

- Provider 输入身份映射、主题能力声明和字段标准化。
- AkShare 空结果、异常响应、字段缺失和日期解析。
- 融资事件去重、金额/币种规范化和来源 ID 稳定性。
- 缺口状态计算和内部优先规则。
- 多来源冲突识别、来源完整性和外部证据快照哈希。
- Provider 错误分类、缓存命中、限流和超时处理。

### 集成测试

- 管理员配置和启停外部 Provider。
- 内部数据完整时不请求外部数据。
- 内部融资为空时请求已启用融资 Provider，并返回外部来源。
- 未配置融资 Provider 时返回可解释的 `unsupported`，不返回伪造事实。
- 外部结果能进入统一调查响应、报告来源索引和 Claim Ledger。

### E2E 测试

- 询问“某企业融资历程”时，验证内部有数据不触发外部调用。
- 询问内部无融资记录企业时，验证外部补数、来源展示和缺失措辞。
- 验证内外部金额或日期冲突时并列展示，不静默覆盖。
- 验证外部 Provider 不可用时系统仍返回内部结果和降级说明。

## 预期结果

当用户询问企业融资、财务、股东或新闻时，系统应按以下逻辑工作：

1. 解析并确认企业身份。
2. 根据用户意图生成主题查询计划。
3. 查询内部只读数据并计算主题覆盖状态。
4. 仅对缺失、过期、部分覆盖或冲突主题调用外部 Provider。
5. 统一去重、登记来源和计算证据状态。
6. 生成带来源的简答、专题结果或报告。
7. 如果外部数据也无法验证，明确返回数据缺口和已尝试来源，不把“未发现”写成“没有”。
