# 企业尽调智能体

企业尽调模块应作为 Yuxi 智能体体系中的领域智能体 `CompanyDueDiligenceAgent`，而不是一组要求用户理解“简单问答、多跳关系、证据检索”的数据库查询页面。

用户负责在主聊天表达调查目标，系统负责从问题或可选上下文识别企业、理解调查意图、选择受控工具、校验事实来源，并按用户要求输出摘要、列表、关系结果、专题报告或完整报告。独立页面只负责全局质量与性能评测，不再形成第二套企业查询逻辑。

当前实现已包含企业解析、结构化查询、最多三跳关系、文本证据、十二章节报告、质量/性能评测、主聊天统一调查入口和一个管理员评测页面。本页同时说明当前确定性规则边界与后续可选在线 LLM，不把未接入能力描述成已上线能力。

完整链路说明见《[企业尽调智能体全链路与效果论证逐字稿](company-due-diligence-end-to-end-script.md)》，开发拆解见《[企业尽调智能体实现逐字稿](company-due-diligence-implementation-guide.md)》，任务清单位于 `tasks/company-due-diligence/README.md`。

## 核心决策

- 广东企业 MySQL 仅只读接入，是企业事实主库；Neo4j、Milvus、MinIO 归档和评测快照都是可重建派生产物。
- 平台启动时幂等注册唯一 slug 为 `company-due-diligence` 的全局共享 Agent，所有有权限用户读取同一条全局配置和同一组工具白名单。
- `t_enterprise.eid` 是系统内部稳定主键，不是普通用户必须知道或填写的查询条件。
- `question` 是唯一必填业务输入；企业名称、股票代码和统一社会信用代码可从问题中自动提取，企业搜索仅作为可选上下文辅助。
- 名称存在歧义时必须让用户确认，不能由 LLM 猜测 `eid`。
- 用户只表达业务问题，不选择“简单问答、多跳关系、证据检索”等内部执行模式。
- 报告既可以由自然语言触发，也可以由独立按钮触发；两种入口归一成相同意图对象，进入同一个编排链路。
- 输出形式由用户意图决定：问股东就返回股东摘要和列表，问关系就返回关系结论和路径，请求专题报告就只生成指定主题。
- 当前先使用确定性规则实现意图理解；后续 LLM 只能处理复杂意图和已验证事实表达，不能执行任意 SQL/Cypher、决定企业身份或补写无来源事实。
- 缺失、过期、冲突、低置信度和来源不可用必须显式返回，不能被自然语言掩盖。

可编辑全链路图位于 `docs/vibe/2026-08-11-company-due-diligence-end-to-end.drawio`。

## 产品输入模型

### 用户实际输入

普通用户唯一必填的是自然语言调查要求。已确认企业可以通过搜索或对话上下文作为可选辅助，但不是进入页面或提交问题的前置条件。

示例：

- “当前数据覆盖哪些企业？”
- “广东纳睿雷达科技股份有限公司的股东有哪些？”
- “000001.SZ 近三年的企业关系和风险有哪些？”
- “请分析这家企业近三年的企业关系和风险，并用报告形式输出。”
- “生成完整尽调报告。”

用户不需要输入 `eid`，也不需要选择查询引擎或执行模式。无企业的全局统计问题进入 `global_scope`；企业依赖问题缺少唯一主体时返回 `needs_context`；若问题中提到另一家企业，智能体会对第二个主体执行同样的解析和必要消歧。

### 企业上下文

企业上下文不是必填表单字段，而是问题自动解析或当前会话已经确认的可选主体：

```json
{
  "conversation_id": "会话标识",
  "primary_company": {
    "eid": "系统内部主键",
    "name": "标准企业名称",
    "resolution_status": "confirmed"
  },
  "referenced_companies": []
}
```

企业解析优先使用信用代码、股票代码、标准全称等稳定标识。模糊名称只返回候选；只有唯一解析企业可以进入企业事实查询。全局白名单统计不要求单企业上下文。

### 内部意图对象

用户自然语言、当前企业上下文和报告按钮参数统一归一成内部意图对象：

```json
{
  "entities": [
    {"eid": "系统解析结果", "role": "primary_company"}
  ],
  "intent": {
    "topics": ["relations", "risks"],
    "presentation": "topic_report",
    "delivery": "async_task",
    "time_scope": {"type": "recent_years", "years": 3},
    "depth": "detailed",
    "evidence_required": true
  },
  "constraints": {
    "hop_limit": 3,
    "include_low_confidence": false
  }
}
```

内部意图至少拆解：

- `entities`：主企业、目标企业和其他被提及主体。
- `topics`：股东、融资、风险、关系、知识产权、新闻或完整尽调等业务主题。
- `time_scope`：当前、指定日期、时间区间或近若干年。
- `depth`：简洁、标准或详细。
- `presentation`：摘要、列表、关系结果、专题报告或完整报告。
- `delivery`：同步响应或异步任务。
- `constraints`：最大跳数、证据数量和低置信度策略等系统约束。

这些字段由规则、快捷入口和后续 LLM 意图理解共同生成，不作为普通用户需要填写的高级表单。

## 领域智能体架构

```text
主聊天中的企业尽调智能体
                    │
                    ▼
          CompanyDueDiligenceAgent
                    │
                    ├── EntityResolutionTool
                    ├── StructuredQueryTool
                    ├── GraphPathTool
                    ├── EvidenceSearchTool
                    ├── ReportGenerationTool
                    └── QualityValidationTool
                    │
                    ▼
          统一响应与 presentation 路由
```

### `EntityResolutionTool`

- 建立或更新企业上下文。
- 将名称、简称、信用代码或股票代码解析成唯一企业。
- 返回 `resolved`、`ambiguous`、`not_found` 或 `source_unavailable`。
- LLM 可以提取用户提到的名称，但不能直接决定最终 `eid`。

### `StructuredQueryTool`

- 查询工商信息、股东出资、产品、融资、财务、风险、许可和知识产权。
- 只允许白名单业务查询，不暴露任意 SQL。
- 金额、比例、日期和分页由确定性代码处理。

### `GraphPathTool`

- 查询共同股东、投资关系和最多三跳的企业关系路径。
- 使用稳定节点 ID、明确方向和关系来源。
- Neo4j 在线但没有激活投影时返回来源不可用，不伪装成无路径。

### `EvidenceSearchTool`

- 检索行政处罚、环保处罚、许可、专利摘要、产品描述和可唯一映射新闻。
- 必须按企业、证据类型、日期和索引版本过滤。
- 文本证据不能脱离结构化企业身份单独成为确定性事实。

### `ReportGenerationTool`

- 接收已经归一化的专题或完整报告意图。
- 锁定企业、数据、图谱、证据索引和配置版本。
- 支持异步进度、取消、章节重试、JSON/Markdown 产物和 checksum。
- 报告按钮只构造明确的报告意图，不绕过领域智能体另建一条流程。

### `QualityValidationTool`

- 对事实、关系、路径、证据和来源建立 Claim Ledger。
- 检查企业身份、来源完整性、冲突、时效、置信度和版本一致性。
- 校验失败时拒绝生成确定结论；LLM 输出失败时回退到确定性模板。

## 执行编排

```text
1. 读取会话企业上下文和用户自然语言
2. 提取被提及企业并完成必要消歧
3. 解析主题、时间、深度、presentation 和 delivery
4. 生成受控工具计划
5. 并行或串行执行 MySQL、Neo4j、Milvus 工具
6. 合并 Claim Ledger、来源和数据质量状态
7. 执行确定性质量校验
8. 生成与原始意图一致的统一响应
9. 前端按 presentation 动态渲染
```

简单股东问题只需要短链路结构化查询；企业关系问题调用图谱工具；风险解释可以组合结构化风险与文本证据；专题或完整报告进入异步报告工具。工具是否被调用由智能体决定，不由用户手工选择。

## 统一输出模型

```json
{
  "status": "complete",
  "understood_request": {
    "topics": ["shareholders"],
    "presentation": "summary_with_list",
    "delivery": "sync",
    "time_scope": {"type": "current"}
  },
  "entities": [],
  "summary": "面向用户的直接结论",
  "findings": [],
  "facts": [],
  "relations": [],
  "paths": [],
  "evidence": [],
  "sources": [],
  "data_quality": {
    "source_status": "available",
    "missing_fields": [],
    "stale_fields": [],
    "conflicts": [],
    "warnings": []
  },
  "presentation": {
    "type": "summary_with_list",
    "components": ["summary", "shareholder_table"]
  },
  "task": null
}
```

字段职责：

- `understood_request`：让用户确认系统如何理解其调查要求。
- `summary`：直接回答用户问题，不强制输出无关章节。
- `findings`：按主题组织关键发现和风险提示。
- `facts / relations / paths / evidence / sources`：支撑结论的可追溯数据。
- `data_quality`：区分真实无数据、来源不可用、过期、冲突和低置信度。
- `presentation`：通知前端如何展示，不是用户预先选择的查询模式。
- `task`：仅在异步专题报告或完整报告时返回任务标识和进度。

### 输入输出一致性示例

| 用户输入 | 内部策略 | 主要输出 |
| --- | --- | --- |
| “这家企业的股东有哪些？” | 结构化股东查询 | 股东摘要、股东列表、来源和数据日期 |
| “A 企业和 B 企业有什么关系？” | 解析两个主体并执行图路径 | 关系结论、完整路径、方向、跳数和来源 |
| “分析近三年的风险” | 风险结构化查询 + 必要证据 | 风险摘要、事件列表、时效和缺失声明 |
| “用报告形式分析近三年的关系和风险” | 图路径 + 风险 + 专题报告 | 异步任务和关系/风险专题报告 |
| 点击“生成完整尽调报告” | 标准完整报告意图 | 十二章节异步报告 |

## 前端交互

目标工作台保留企业搜索/确认区和一个自然语言输入框，不再要求用户选择“简单问答、多跳关系、证据检索”。

结果区按 `presentation.type` 动态组合：

- 直接摘要与事实卡片。
- 股东、融资、风险、知识产权等业务列表。
- 企业关系路径列表。
- 专题报告或完整报告任务进度与产物。
- 来源、证据和数据质量详情。

未来可新增交互式关系图组件，消费现有 `entities / relations / paths`。图谱展示是关系结果的可视化扩展，不改变后端事实契约，也不成为新的查询模式。

## 多跳与 LLM 边界

多跳关系由 Neo4j 中的受控路径模板实现，不依赖向量检索自行拼接路径。公开冻结基线包含 `120` 道问题、`541` 个节点和 `1,985` 条边：TF-IDF 向量基线严格准确率为 `55.83%`、多跳准确率为 `0%`；GraphRAG 严格准确率和多跳准确率均为 `100%`。该结果只说明确定性图路径相对纯向量基线更适合关系问题，因为公开基线人工复核覆盖率仍为 `0%`，不能替代广东企业正式业务 Golden。

后续接入 LLM 时遵循：

- LLM 提取企业名称和调查意图，企业身份仍由确定性解析器确认。
- LLM 只能读取通过质量校验的 Claim Ledger。
- 输出中的每个企业事实必须能映射到 `source_id`。
- 确定性后置校验检查实体、数值、日期、路径和来源引用。
- 校验失败时回退模板答案，不用更流畅的错误回答覆盖正确结构化结果。

## 质量评测

目标评测分为五层：

1. **企业上下文**：主体解析正确率、歧义召回率和错误自动选中率。
2. **意图理解**：主题、时间范围、输出形式、交付方式和目标企业识别准确率。
3. **工具编排**：必要工具召回率、无关工具调用率、参数约束正确率和失败降级语义。
4. **事实质量**：字段、关系、路径、证据、拒答、时效、来源覆盖和幻觉率。
5. **输入输出一致性**：输出是否覆盖用户要求的主题、是否遗漏必要结果、是否加入无关章节、`presentation` 是否匹配用户要求。

报告还需评估专题范围一致率、章节完整率和任务交付成功率。LLM 表达质量可以使用人工评分或文本指标辅助评估，但不能替代事实、路径和来源的严格比较。

正式发布门禁要求幻觉率为 `0`、证据覆盖率为 `100%`、无新增严格失败，并使用包含 `human_verified` 样本且冻结 checksum 的广东企业 Golden。当前自动烟测和公开基线不能替代人工业务验收。

## 非目标

- 不修改或补充原广东企业数据库表。
- 不将 Neo4j 或 LLM 作为第二事实主库。
- 不允许智能体执行任意 SQL、任意 Cypher 或无限关系遍历。
- 不让普通用户填写数据库主键或理解底层查询引擎。
- 不以回答流畅度、节点数量或未人工复核的公开基线代替业务准确率。
- 本轮不接入在线 LLM，也不实现交互式关系图；现有 `entities / relations / paths` 已冻结为后续图展示输入。
