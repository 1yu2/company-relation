# 企业尽调智能体

企业尽调智能体是 Yuxi 在企业数据场景中的长期建设方向。系统以现有广东企业 MySQL 为只读事实主库，通过统一数据契约提供企业查询、完整尽调报告和多跳关系分析，并使用 Neo4j、Milvus、冻结 Golden 数据集完成关系推理、文本证据检索、结果质量评测和系统性能评测。

当前页面描述目标架构和阶段验收，不代表所有能力已经完成。现有 30 家 AkShare 企业关系链路保留为公开数据回归基线，广东企业数据库接入、报告服务和新评测集需要按本文路线逐步实现。

逐项实施说明见《[企业尽调智能体实现逐字稿](company-due-diligence-implementation-guide.md)》，可并行/串行执行的任务清单位于仓库根目录 `tasks/company-due-diligence/README.md`。

## 核心决策

- 原广东企业 MySQL 仅只读接入，不修改、不补充、不清洗回写原始表。
- `t_enterprise.eid` 作为当前企业内部主键；信用代码、股票代码和标准化名称作为外部身份映射。
- MySQL 是唯一事实主库，Neo4j、Milvus 和 JSON 评测快照均为可重建的派生产物。
- AkShare 默认不参与主查询，只在后续按需补充上市公司公告、最新公开披露和数据时效核验。
- 单字段查询、完整报告和多跳路径使用同一套 `Entity / Relation / Fact / Evidence / Source` 输出契约。
- 缺失、过期、冲突和低置信度数据必须显式返回，不能由 LLM 静默补全。

可编辑架构图源文件位于本地开发目录 `docs/vibe/2026-08-10-enterprise-due-diligence-architecture.drawio`；该目录默认不提交，本文正文保留正式架构边界。

## 系统链路

```text
广东企业 MySQL（只读事实主库）
        │
        ▼
只读 Repository 与健康连接池
        │
        ▼
企业实体解析与统一数据契约
        │
        ├── SQL 查询服务：属性、出资、融资、财务、风险统计
        ├── Neo4j 投影：股东、投资、知识产权、多跳路径
        ├── Milvus 索引：新闻、处罚文书、许可内容、专利摘要
        └── 冻结快照：checksum、Golden 数据集、问题复现
                       │
                       ▼
                LangGraph 尽调编排器
                       │
                       ├── 企业查询 API
                       ├── 完整报告 API
                       ├── 结果质量评测
                       └── 系统性能评测
```

## 统一输入输出

### 输入

查询入口至少支持以下企业标识：

- `eid`
- 统一社会信用代码
- 股票代码
- 企业全称
- 企业简称，但必须返回候选并要求消歧

请求应区分查询和报告：

```json
{
  "company": "企业名称或唯一标识",
  "query": "主要股东还投资了哪些企业？",
  "max_depth": 3,
  "as_of_date": "2026-08-10"
}
```

完整报告请求：

```json
{
  "company": "企业名称或唯一标识",
  "sections": [
    "profile",
    "shareholders",
    "financing",
    "financials",
    "risks",
    "intellectual_property",
    "news",
    "relations"
  ],
  "relation_depth": 3
}
```

### 输出

所有查询和报告事实必须统一返回：

```json
{
  "answer": "面向用户的答案或章节摘要",
  "facts": [],
  "relations": [],
  "paths": [],
  "evidence": [],
  "sources": [],
  "data_quality": {
    "as_of_date": "2025-12-01",
    "missing_fields": [],
    "stale_fields": [],
    "conflicts": [],
    "low_confidence_relations": []
  },
  "latency_ms": 0
}
```

来源至少包含来源系统、表名、原始记录 ID、数据日期和更新时间。LLM 只负责组织已验证事实，不生成没有来源的企业事实。

## 只读数据接入

数据库接入层应满足：

- 使用 SQLAlchemy 连接池，默认小连接池、零或受限溢出、`pool_pre_ping` 和连接回收。
- 使用只读数据库账号；若现有账号权限较高，应用层仍需强制只读事务。
- 所有 SQL 参数化，禁止将用户输入拼接到表名、字段名或条件表达式。
- 对允许访问的表和查询模板建立白名单，不开放任意 SQL 给智能体。
- 大表查询必须命中 `eid`、信用代码、时间或业务索引，不允许无界正文扫描。
- 设置连接、读取、池等待和单条 SQL 执行超时。
- API 请求结束后归还连接，报告工作流并行度不得超过连接池和数据库承受范围。
- 记录查询模板、耗时、返回行数和错误类型，但不记录密码、完整连接串或敏感个人字段。

接入层只做应用内标准化，不写回原表。复杂名称映射在项目自己的配置、缓存或派生快照中维护。

## 查询能力

### 精确结构化查询

- 企业基本信息、注册资本、实收资本、法人和状态。
- 当前和历史股东、出资比例、认缴和实缴。
- 产品、融资轮次、融资金额和投资机构。
- 财务指标、行政处罚、许可和经营异常统计。
- 专利、商标、著作权数量、类型和时间分布。

这类问题由 MySQL 返回精确事实，LLM 不负责计算金额或猜测缺失字段。

### 多跳关系查询

- 企业 → 股东 → 其他企业。
- 企业 → 融资事件 → 投资机构 → 其他被投企业。
- 企业 → 专利/商标 → 共同权利主体。
- 企业 → 监管机关 → 同类处罚或许可企业。

高置信度路径必须使用稳定 ID。仅按企业名、自然人姓名或产品名推导的关系作为候选，不进入严格事实答案。

### 文本证据查询

- 新闻原文和摘要。
- 行政处罚文书和 PDF 内容。
- 行政许可内容。
- 专利摘要和产品描述。

文本检索结果必须回连结构化企业 `eid`，否则只能作为未归属候选证据。

## 完整尽调报告

报告工作流应依次完成企业身份确认、并行取数、图关系扩展、文本证据检索、事实校验和章节生成。首版报告包含：

1. 企业身份和数据截止日期。
2. 工商基本信息。
3. 当前及历史股东结构。
4. 认缴、实缴和持股比例。
5. 融资历程与投资机构。
6. 产品和业务概览。
7. 财务指标和趋势。
8. 行政处罚、环保、经营异常和许可。
9. 专利、商标和著作权。
10. 新闻舆情和重大事件。
11. 高置信度企业多跳关联。
12. 数据来源、时效、缺失、冲突和置信度声明。

报告至少落盘完整 JSON 和便于阅读的 Markdown。后续可以增加 PDF，但 PDF 不是首版验收前提。

## AkShare 定位

首版主链路不依赖 AkShare。现有采集脚本和 30 家公开快照继续保留，用于：

- 公开数据链路回归测试。
- 巨潮资讯公告补充。
- 用户明确询问“最新”时进行公开披露核验。
- 对广东数据库中部分上市公司字段做来源对照。

AkShare 数据不能静默覆盖 MySQL 事实；当两个来源不一致时，必须同时返回来源和数据日期。

## 分阶段建设

### 阶段 0：文档和数据审计

**当前状态：已完成。**

交付物：

- 广东企业数据库只读审计。
- 系统架构、数据边界和实施路线。
- 现有 AkShare 基线的重新定位。

验收：不包含敏感连接信息，明确可用表、数据质量、时效和映射风险。

### 阶段 1：数据接入

交付物：

- 只读 `MysqlEnterpriseRepository` 和连接池配置。
- 企业身份解析器。
- 企业、股东、产品、融资、风险和知识产权 DTO。
- 来源、时效和数据质量输出。
- 从 MySQL 导出冻结评测快照的脚本。

验收：

- 不修改原始表。
- 连接失败、超时和池耗尽显式报错。
- 任意有效 `eid` 可返回统一企业摘要。
- 所有事实可追溯到来源表、记录 ID 和更新时间。
- 相关单元测试和真实只读集成测试通过。

### 阶段 2：查询、报告和多跳关系

交付物：

- 企业属性、股东、融资、风险和知识产权查询 API。
- 完整尽调报告 API 与 JSON/Markdown 产物。
- 从 MySQL 生成 Neo4j 高置信度关系投影。
- 企业关系路径和证据输出。
- 新闻、处罚和专利文本证据检索。

验收：

- 单字段查询不依赖 LLM 计算。
- 报告所有章节显式说明无数据和过期数据。
- 多跳路径包含节点、关系、来源和置信度。
- Neo4j 可以从 MySQL 全量重建，不成为第二事实主库。
- 任意低置信度名称关系不会被包装成确定控制关系。

### 阶段 3：结果质量评测

评测数据必须来自冻结 MySQL 快照，并由人工复核，不继续使用“系统生成答案再评价系统”的单一口径。

评测集合至少覆盖：

- 企业基本属性。
- 股东和出资明细。
- 融资和投资机构。
- 风险、许可和知识产权。
- 单跳和多跳企业关系。
- 无答案、过期数据和关系冲突。
- 完整尽调报告。

核心指标：

| 指标 | 定义 |
| --- | --- |
| 字段严格准确率 | 值、单位、日期和来源全部正确 |
| 关系严格准确率 | 实体、关系、方向和属性全部正确 |
| 多跳路径准确率 | 完整路径与人工金标准一致 |
| 证据覆盖率 | 每个事实都有可追溯来源 |
| 拒答准确率 | 无证据或低置信度时正确拒答或降级 |
| 幻觉率 | 输出中不存在于证据的数据占比 |
| 报告章节完整率 | 应输出章节和必要声明是否齐全 |
| 时效声明准确率 | 过期、缺失和冲突是否被正确标识 |

首版回归门禁建议：幻觉率为 0、证据覆盖率为 100%、无新增严格失败、报告必要章节完整率为 100%。其他准确率门槛根据首批人工 Golden 基线确定，不能预设虚假的 100%。

### 阶段 4：系统性能评测

性能评测必须记录数据版本、机器配置、连接池参数、缓存状态、并发数和是否包含在线 LLM。

测试维度：

- MySQL 单表、关联和聚合查询。
- Neo4j 单跳、两跳和最多三跳路径查询。
- 文本证据检索。
- 企业综合查询 API。
- 结构化报告数据聚合。
- 包含在线 LLM 的完整报告生成。
- 10、20、50 并发下的错误率、吞吐和池等待。
- 冷缓存和热缓存分别统计。

初始工程目标：

| 场景 | 初始目标 |
| --- | ---: |
| 企业基本信息查询 | P95 < 500 ms |
| 股东、融资、风险列表 | P95 < 1 s |
| 最多三跳关系查询 | P95 < 3 s |
| 不含 LLM 的报告数据聚合 | P95 < 5 s |
| 包含在线 LLM 的完整报告 | P95 < 30 s，单独记录模型耗时 |
| 10 并发核心查询 | 错误率 < 1% |
| 数据库连接池 | 无泄漏、无非预期溢出、池等待可观测 |

这些数值是首版工程目标，不是当前已达成结果。达到目标后仍需保存逐请求明细、P50/P95/P99、最大延迟、错误分类和吞吐报告。

## 非目标

- 不修改或补充原广东企业数据库表。
- 不将 Neo4j 作为第二事实主库。
- 不允许智能体执行任意 SQL。
- 不以节点或边数量代替事实准确率和来源覆盖。
- 不将名称相同直接解释为实际控制、投资或业务关系。
- 不使用未人工复核的派生 Golden 宣称生产准确率。
