# 企业尽调智能体实现逐字稿

本文是一份可以从头到尾逐项盘点的实施逐字稿。它把《企业尽调智能体》总体方案转换成明确的开发顺序，回答以下问题：当前有什么数据、数据如何只读接入、接入后如何检索、简单问答如何实现、多跳查询如何实现、完整报告如何生成、结果如何评测、性能如何评测，以及前端如何承载查询和评测。

本文描述的是**目标实现路径**。截至 2026 年 8 月 10 日，广东企业数据库审计和 30 家 AkShare 公开关系基线已经完成；广东企业只读接入、问答、报告、Neo4j 投影、新 Golden 和前端尽调工作台仍待实现。

执行任务清单见仓库根目录的 `tasks/company-due-diligence/README.md`。

## 一、先明确本系统要解决什么问题

逐字说明：

> 我们要建设的不是一个只能生成长报告的展示程序，而是一套企业尽调查询系统。用户既可以问“这家公司的注册资本是多少”“当前股东有哪些”，也可以问“这两家公司通过哪些共同股东关联”，还可以一次性生成完整尽调报告。无论是短问答、多跳路径还是完整报告，都必须使用同一套事实、关系、证据和来源契约。

系统首版必须同时满足三类使用场景：

1. **简单问答**：企业基本信息、股东及出资、产品、融资、处罚、许可、知识产权和财务指标。
2. **关系分析**：共同股东、融资机构网络、历史股东、共同知识产权主体和最多三跳的企业关联路径。
3. **完整报告**：按固定章节聚合结构化事实、关系路径和文本证据，输出 JSON 和 Markdown 报告。

系统不以“模型回答得像”为成功标准，而以以下结果为成功标准：

- 查到的值与源数据一致；
- 每个重要事实可以定位来源表、来源记录和数据时点；
- 没有数据时明确说没有，不使用模型常识补齐；
- 低置信度名称关系只作为候选线索，不包装成确定事实；
- 同一个问题可以通过冻结数据版本复现；
- 前端可以查看答案、报告、证据、质量指标和性能指标。

## 二、当前已经有什么数据

### 2.1 广东企业 MySQL：主数据源

逐字说明：

> 当前最有价值的数据不是原来的 30 家公开演示快照，而是现有广东企业 MySQL。它包含 924 家广东上市企业及多域尽调数据，应该作为企业尽调智能体的只读事实主库。我们不修改它，也不向它补表；所有统一、清洗、关系构建和评测都在应用层或可重建投影中完成。

当前已审计的数据资产如下：

| 数据域 | 核心表 | 当前规模 | 当前用途 | 主要限制 |
| --- | --- | ---: | --- | --- |

需要特别说明以下数据质量事实：

- `t_enterprise.eid` 是当前最稳定的企业内部主键。
- 924 家企业均有企业名称、统一社会信用代码、注册资本、法人、状态和区域代码。
- 当前股东 7,305 条，历史股东 5,866 条；只有部分股东可以通过稳定 ID 连接到其他企业。
- 已识别 232 个关联多家企业的共同股东键，其中 121 个有稳定 ID，111 个只能依赖名称。
- 自然人姓名、同名产品和单一新闻名称命中只能作为低置信度候选。
- 财务、新闻和 `t_enterprise_equity` 不能直接按当前字段完整映射到 924 家企业，首版必须明确覆盖范围。

完整审计依据保存在本地开发记录 `docs/vibe/2026-08-10-guangdong-enterprise-data-audit.md`；`docs/vibe` 默认不提交，正式数据结论已在本节完整列出。

### 2.2 AkShare 公开数据：回归和补充数据源

逐字说明：

> AkShare 不再与广东企业数据库并列为双主库。现有 30 家公开上市公司快照继续保留，因为它无敏感连接依赖、可以公开复现，适合做开发回归和演示；后续也可以用于公告、最新公开披露和主库时效核验，但不能静默覆盖 MySQL 中的事实。

当前公开基线已经具备：

- 30 家企业冻结快照；
- JSON 校验和 Neo4j 导入；
- TF-IDF、确定性 GraphRAG 和 Cypher 三策略对照；
- JSON、JSONL 和 Markdown 评测结果；
- TF-IDF 55.83%、GraphRAG 100%、Cypher 100% 的当前冻结题库结果。

这些数字不能直接代表新尽调系统质量，因为当前 Golden 人工复核率为 0%，GraphRAG 也只是确定性图遍历，不包含在线 LLM。它只是一条公开回归基线。

### 2.3 Yuxi 现有基础设施：复用，不重复创建

逐字说明：

> 本项目已经通过 Docker Compose 管理 PostgreSQL、Redis、MinIO、Milvus、Neo4j、API、worker 和 web。尽调系统只增加业务接入和业务 API，不新增一套 PostgreSQL、MinIO、Redis、Neo4j、Milvus 或 MySQL 容器，也不要求重复拉取已有镜像。外部广东 MySQL 通过环境变量只读接入。

存储职责固定如下：

| 存储 | 职责 | 是否事实主库 |
| --- | --- | --- |
| 广东企业 MySQL | 企业、股东、融资、风险、知识产权、财务和新闻原始事实 | 是 |
| Yuxi PostgreSQL | 查询任务、报告任务、评测数据集元数据、运行状态和结果索引 | 否 |
| Neo4j | 从 MySQL 投影的高置信度关系和多跳路径 | 否，可重建 |
| Milvus | 新闻、处罚文书、许可内容、专利摘要和产品描述向量索引 | 否，可重建 |
| MinIO | 冻结快照、评测数据集和导出报告等文件产物 | 否 |
| Redis | 任务事件、进度、取消信号和短期缓存 | 否 |

## 三、第一步：只读接入广东企业 MySQL

逐字说明：

> 第一项开发任务不是写问答提示词，而是建立一个健康、限流、可观测的只读 MySQL 接入层。所有后续 SQL 查询、图谱投影和评测快照都必须经过这一层。应用启动时只验证连接和必要表，不执行建表、迁移、更新或自动修复。

### 3.1 配置读取

- 从 `.env` 或容器环境读取独立配置，例如 `COMPANY_DD_MYSQL_URL`。
- 不把完整 DSN 写入日志、异常、接口响应、测试快照或文档。
- 如果现有 `.env` 使用 Python 表达式而不是标准 DSN，应在配置解析层显式处理或先改成标准环境变量格式，不能通过 `eval` 执行。
- 健康检查只返回“已配置、可连接、延迟、连接池状态、必要表是否存在”，不返回主机、用户名和密码。

### 3.2 健康连接池

首版连接池基线：

```text
pool_size = 2
max_overflow = 0
pool_pre_ping = true
pool_recycle = 300s
pool_timeout = 5s
connect_timeout = 8s
statement_timeout = 5~10s
session = READ ONLY
```

生产参数可以通过性能评测调整，但以下约束不变：

- 不允许无限连接和非预期溢出；
- 每条大表查询必须带企业键、时间范围、索引条件和分页上限；
- 超时应显式失败并记录数据源阶段耗时，不能无限重试；
- 连接归还、池等待和超时需要形成指标；
- 禁止执行 `INSERT`、`UPDATE`、`DELETE`、`CREATE`、`ALTER`、`DROP`、`TRUNCATE`。

### 3.3 Repository 边界

只读 Repository 应按业务域组织，而不是把任意 SQL 暴露给 LLM：

- `EnterpriseRepository`：企业身份和基本信息；
- `ShareholderRepository`：当前/历史股东及出资；
- `ProductRepository`：产品；
- `FinanceRepository`：融资；
- `RiskRepository`：处罚、异常和许可；
- `IntellectualPropertyRepository`：专利、商标和著作权；
- `FinancialMetricRepository`：财务指标；
- `NewsRepository`：新闻元数据和允许读取的文本字段。

每个方法都应该是明确的业务查询，例如 `list_current_shareholders(eid, limit)`，而不是 `execute_sql(sql)`。

### 3.4 这一步的输入输出

输入：

```json
{
  "operation": "get_enterprise",
  "eid": "内部企业标识"
}
```

输出：

```json
{
  "record": {},
  "source_table": "t_enterprise",
  "source_key": "脱敏后的稳定记录标识",
  "data_as_of": "2025-12-01",
  "local_updated_at": "2025-12-08",
  "latency_ms": 0
}
```

验收重点：通过集成测试证明查询成功、写操作被拒绝、连接池无泄漏、超时能回收连接、日志不包含完整 DSN。

## 四、第二步：建立企业身份解析

逐字说明：

> 用户输入的可能是 `eid`、企业全称、简称、统一社会信用代码或股票代码。任何业务查询前都必须先解析成唯一企业身份。解析失败时返回候选列表；不能因为名称相似就自动选中一家企业。

解析优先级：

1. `eid` 精确匹配；
2. 统一社会信用代码精确匹配；
3. 股票代码精确匹配；
4. 企业标准全称精确匹配；
5. 规范化名称精确匹配；
6. 模糊名称只返回候选，不自动进入事实查询。

建议统一输入：

```json
{
  "company_ref": {
    "eid": null,
    "name": "企业名称或简称",
    "unified_social_credit_code": null,
    "stock_code": null
  }
}
```

统一解析结果：

```json
{
  "status": "resolved",
  "entity": {
    "eid": "稳定内部标识",
    "name": "标准企业名称",
    "unified_social_credit_code": "脱敏展示值或按权限返回",
    "stock_code": "股票代码"
  },
  "match_method": "stock_code_exact",
  "confidence": "high",
  "candidates": []
}
```

如果存在多个候选，返回 `status=ambiguous`，前端要求用户选择；如果不存在，返回 `status=not_found`。这两个状态都不能继续生成确定性事实答案。

## 五、第三步：冻结统一输入输出契约

逐字说明：

> 简单问答、报告和评测不能各自设计一套结果格式。我们先定义统一事实契约，再让 SQL、Neo4j、Milvus 和 LLM 都围绕这套契约工作。这样前端、评测器和导出程序可以复用同一份结果。

### 5.1 统一查询输入

```json
{
  "company_ref": {"name": "目标企业"},
  "question": "这家公司的当前股东及出资情况是什么？",
  "mode": "qa",
  "as_of": null,
  "hop_limit": 3,
  "top_k": 10,
  "include_low_confidence": false
}
```

`mode` 首版支持：

- `qa`：简单问答或多跳问题；
- `report`：完整报告；
- `evidence`：只返回检索证据，便于调试和人工复核。

### 5.2 统一查询输出

```json
{
  "request_id": "请求标识",
  "query_type": "shareholder_list",
  "answer": "面向用户的简短答案",
  "entities": [],
  "facts": [],
  "relations": [],
  "paths": [],
  "evidence": [],
  "sources": [],
  "data_quality": {
    "status": "complete",
    "warnings": [],
    "missing_fields": [],
    "conflicts": [],
    "lowest_confidence": "high"
  },
  "latency_ms": {
    "total": 0,
    "identity": 0,
    "mysql": 0,
    "neo4j": 0,
    "milvus": 0,
    "llm": 0
  }
}
```

每个 `Fact` 至少包含：

```json
{
  "subject_id": "企业或关系主体标识",
  "predicate": "registered_capital",
  "value": "规范化值",
  "display_value": "面向用户的值",
  "unit": "CNY",
  "effective_date": null,
  "confidence": "high",
  "source_id": "来源标识"
}
```

每个 `Source` 至少包含：

```json
{
  "source_id": "来源标识",
  "source_type": "mysql",
  "source_name": "t_enterprise",
  "record_key": "可追溯但不泄露凭据的记录键",
  "data_as_of": "数据业务日期",
  "retrieved_at": "本次查询时间"
}
```

统一契约必须显式表达：无数据、字段缺失、数据过期、来源冲突、映射置信度不足和查询阶段超时。

## 六、第四步：先实现简单问答

逐字说明：

> 首版不能等完整报告和图谱全部完成后才可用。我们先实现结构化简单问答，让用户可以精确查询企业基本信息、股东、产品、融资、风险、许可、知识产权和财务。简单问答先走规则化意图与参数解析，再调用白名单 Repository；LLM 只负责理解表达和组织答案，不生成数据库里没有的值。

### 6.1 简单问答完整链路

```text
用户问题
  → 企业身份解析
  → 问题类型识别
  → 参数抽取与校验
  → 只读 MySQL Repository
  → 事实规范化
  → 来源与时效校验
  → 答案组织
  → 统一结果输出
```

### 6.2 首版问题类型

| 问题类型 | 示例 | 主查询源 |
| --- | --- | --- |
| 企业基本信息 | 注册资本、法人、状态、成立时间、经营范围 | `t_enterprise` |
| 当前股东 | 当前股东有哪些、持股比例多少 | `t_partners_alls` |
| 历史股东 | 历史股东和退出时间 | `t_partners_alls` |
| 股东出资 | 认缴、实缴、出资比例和出资明细 | `t_partners_alls` |
| 产品 | 有哪些产品、产品描述和渠道 | `t_company_products` |
| 融资 | 融资轮次、金额、时间、投资机构 | `t_company_finance` |
| 风险 | 行政处罚、环保处罚、经营异常 | 风险相关表 |
| 许可 | 许可数量、类型和有效期 | `t_license_info` |
| 知识产权 | 专利、商标、著作权数量和列表 | 知识产权相关表 |
| 财务 | 指标时间序列和覆盖范围 | 财务指标表 |

### 6.3 简单问答示例

输入：

```json
{
  "company_ref": {"stock_code": "示例股票代码"},
  "question": "这家公司的注册资本是多少？",
  "mode": "qa"
}
```

输出逻辑：

1. 股票代码精确解析为 `eid`；
2. 从 `t_enterprise` 查询注册资本；
3. 规范化金额和币种；
4. 返回一句简答；
5. 同时返回对应 `Fact`、`Source`、数据时点和 MySQL 耗时；
6. 如果字段缺失，回答“当前数据源未提供”，不能推测。

回答文本示例：

```text
根据企业主表记录，该企业注册资本为〔规范化金额〕。该数据的业务时点为〔日期〕；如需当前工商状态，应进一步通过公开披露进行时效核验。
```

### 6.4 问答中的拒答规则

以下情况必须拒绝或降级：

- 企业身份存在多个候选；
- 请求字段不在允许的数据域；
- 只有低置信度名称关系，却要求确定性控制关系；
- 查询超时或关键来源不可用；
- 数据已明显过期且问题要求“当前”“最新”；
- 多个来源冲突且没有明确优先规则。

拒答也必须返回原因、已查来源和下一步建议，不能只返回“无法回答”。

## 七、第五步：构建 Neo4j 可重建关系投影

逐字说明：

> MySQL 适合查精确字段，但共同股东、融资机构网络和多跳关联路径不应该在每次请求中临时拼接大量 SQL。我们从 MySQL 生成带版本的 Neo4j 投影。Neo4j 只负责关系遍历，不成为第二事实主库；任何节点和关系都必须能追溯到 MySQL 来源并能够全量重建。

### 7.1 首版图谱对象

节点：

- `Company`：以 `eid` 为稳定键；
- `Shareholder`：稳定 `stock_id` 优先，标准化名称为候选键；
- `FinancingEvent`：企业、轮次、时间和来源记录组合键；
- `Investor`：投资人 ID 优先；
- `Patent`、`Trademark`、`Copyright`：使用稳定业务号；
- `Punishment`、`License`：使用来源记录稳定键；
- `Regulator`：标准化机关名称。

关系：

- `HOLDS`：股东持有企业；
- `RECEIVED_FINANCING`：企业获得融资；
- `INVESTED_IN`：投资人参与融资；
- `OWNS_PATENT`、`OWNS_TRADEMARK`、`OWNS_COPYRIGHT`；
- `PUNISHED_BY`、`LICENSED_BY`。

每条关系至少保存：来源表、来源记录键、当前/历史状态、有效日期、投影版本和置信度。

### 7.2 置信度规则

- **高置信度**：`eid`、信用代码、股票代码、稳定股东 ID、融资投资人 ID、专利申请号等稳定键。
- **中置信度**：标准企业全称一致，并且区域、法人、信用代码片段或其他辅助字段一致。
- **低置信度**：自然人姓名、产品名称、新闻中的单字段名称命中。

默认多跳事实答案只使用高置信度关系。中低置信度关系可以在“线索模式”返回，但必须标明候选性质。

### 7.3 投影过程

```text
读取 MySQL 只读批次
  → 规范化企业与关系键
  → 生成投影快照和 checksum
  → 校验节点、边、孤儿和重复关系
  → 幂等写入 Neo4j 指定版本
  → 记录投影统计
  → 切换当前可查询版本
```

不允许边查边把 LLM 推测关系写进图谱。`RELATED_TO` 不是原始事实，只能在查询时根据基础关系路径派生。

## 八、第六步：实现多跳关系查询

逐字说明：

> 多跳问题必须先解析起点企业、目标企业、允许的关系类型、最大跳数和置信度要求，再执行受控 Cypher。LLM 不直接生成无限制 Cypher；系统使用参数化模板或经过校验的查询计划，最大跳数首版限制为三跳。

首版多跳问题：

1. 企业 → 当前/历史股东 → 其他企业；
2. 企业 → 融资事件 → 投资机构 → 其他被投企业；
3. 企业 → 知识产权 → 共同权利主体或关联企业；
4. 企业 → 处罚/许可机关 → 同类企业；
5. 两家企业之间的最短高置信度路径；
6. 某股东或投资机构关联的企业网络。

多跳输出不能只有自然语言，至少还要返回：

```json
{
  "path_id": "路径标识",
  "hop_count": 2,
  "nodes": [],
  "edges": [],
  "confidence": "high",
  "derivation": "共同股东路径",
  "source_ids": []
}
```

回答时应明确区分：

- “存在一条由稳定股东 ID 支撑的高置信度路径”；
- “仅发现同名主体候选，不能确认实际关联”；
- “在当前最多三跳、当前投影版本中未找到路径”。

## 九、第七步：接入文本证据检索

逐字说明：

> 结构化字段可以回答“有什么”，但新闻、处罚原因、许可内容和专利摘要需要文本证据。我们复用现有 Milvus 和 MinIO，不新增向量数据库或对象存储。文本索引从 MySQL 只读抽取，可以随时删除并重建。

首版建议索引：

- 新闻标题、摘要和允许读取的正文；
- 行政处罚事实、依据、决定和处罚机关；
- 环保处罚内容；
- 行政许可事项和许可内容；
- 专利摘要；
- 产品描述。

每个文本块元数据至少包含：

```json
{
  "document_id": "稳定文档标识",
  "eid": "企业标识",
  "source_table": "来源表",
  "source_record_key": "来源记录键",
  "document_type": "news",
  "published_at": "业务日期",
  "projection_version": "索引版本",
  "checksum": "内容校验值"
}
```

检索流程：

```text
企业身份和问题
  → 先按 eid、文档类型和日期过滤
  → 在过滤结果中向量召回
  → 必要时重排
  → 返回原文片段和元数据
  → 事实核验后进入答案或报告
```

Milvus 检索结果只是证据候选。金额、日期、处罚状态和企业身份等结构化事实仍以 MySQL 为准。

## 十、第八步：用 LangGraph 编排问答

逐字说明：

> 当 SQL、图谱和文本检索都具备后，LangGraph 的职责是选择工具、控制步骤和汇总结果，而不是充当事实数据库。简单字段问题只走短链路；多跳问题走图谱链路；需要解释的风险或新闻问题再增加文本证据链路。

建议节点：

```text
validate_request
  → resolve_company
  → classify_question
  → build_query_plan
  → query_mysql / query_neo4j / retrieve_evidence
  → verify_facts
  → compose_answer
  → attach_sources
  → finalize_metrics
```

路由原则：

- 基本信息、股东列表、融资列表、风险统计等走 MySQL；
- 共同股东、最短路径和投资网络走 Neo4j；
- 新闻解释、处罚原因、许可内容和专利摘要走 Milvus，并回查 MySQL 元数据；
- 一个问题可以并行查询多个源，但最终只输出已验证的事实；
- LLM 输出必须通过事实引用检查，无法匹配 `source_id` 的企业事实不得进入最终答案。

简单问答应支持普通 HTTP 响应；耗时较长的报告和评测使用后台任务与 SSE/轮询进度，复用现有 Tasker 和前端任务模式。

## 十一、第九步：生成完整尽调报告

逐字说明：

> 报告不是把一个长提示词交给模型。报告服务先确定企业身份和数据版本，再并行拉取各章节结构化事实、关系路径和文本证据，形成报告数据包；最后才由模板和 LLM 生成摘要。即使 LLM 不可用，系统仍应能够输出结构化 JSON 和基础 Markdown。

### 11.1 报告输入

```json
{
  "company_ref": {"eid": "企业标识"},
  "sections": [
    "identity",
    "business",
    "shareholders",
    "relations",
    "products",
    "financing",
    "financials",
    "compliance",
    "intellectual_property",
    "news",
    "data_quality"
  ],
  "as_of": null,
  "include_low_confidence_clues": false,
  "output_formats": ["json", "markdown"]
}
```

### 11.2 报告章节

1. 企业身份确认；
2. 工商基本信息；
3. 股权结构与出资；
4. 多跳关联与关联线索；
5. 产品与业务；
6. 融资历程；
7. 财务表现；
8. 经营合规与许可；
9. 知识产权与创新；
10. 新闻舆情；
11. 关键风险和待核验事项；
12. 数据质量、来源和时效声明。

### 11.3 报告执行链路

```text
创建报告任务
  → 锁定企业身份和数据版本
  → 并行查询各章节
  → 汇总事实、路径和证据
  → 章节数据质量检查
  → 生成结构化报告 JSON
  → 生成 Markdown 摘要
  → 保存文件产物与 checksum
  → 返回报告状态和下载信息
```

报告章节状态至少支持：

- `complete`：数据和来源完整；
- `partial`：有结果但字段或覆盖不完整；
- `no_data`：当前来源没有记录；
- `stale`：数据时点不能支撑当前性结论；
- `conflicted`：多个来源存在未解决冲突；
- `failed`：查询或生成失败。

报告不能因为某个非关键章节失败而整体伪装成功；前端应看到章节状态和失败原因。

## 十二、第十步：冻结快照与人工 Golden

逐字说明：

> 没有冻结数据和人工答案，就无法判断改动后到底变好还是变差。我们从 MySQL 只读导出一批经过脱敏的评测快照，并由人工核对简单问题、多跳路径和报告章节。评测不能继续用程序自己生成答案再评价程序自己。

Golden 至少包含三类：

1. **字段问答集**：企业基本信息、股东、出资、产品、融资、风险和知识产权；
2. **关系路径集**：共同股东、投资机构网络、最短路径和无路径问题；
3. **报告 Golden**：选定企业的章节事实、必要来源、缺失声明和人工风险摘要。

每条样本至少保存：

```json
{
  "case_id": "样本标识",
  "dataset_version": "数据集版本",
  "question_type": "registered_capital",
  "input": {},
  "expected_facts": [],
  "expected_paths": [],
  "required_sources": [],
  "expected_refusal": false,
  "review_status": "human_verified",
  "reviewed_at": "人工复核日期"
}
```

冻结产物需要 checksum、生成时间、源数据业务时点、脱敏说明和人工复核状态。评测数据文件不保存数据库密码或完整连接信息。

## 十三、第十一步：结果质量评测

逐字说明：

> 质量评测同时评答案、事实、路径、来源、拒答和报告章节。自然语言相似度只能作为辅助指标，不能代替字段严格匹配和路径严格匹配。

首版核心指标：

| 指标 | 计算重点 |
| --- | --- |
| 字段严格准确率 | 值、单位、日期和企业身份全部正确 |
| 关系严格准确率 | 起点、终点、关系类型、方向和属性正确 |
| 多跳路径准确率 | 节点序列、边序列、方向和跳数与 Golden 一致 |
| 证据覆盖率 | 每个必需事实都存在有效 `source_id` |
| 拒答准确率 | 无数据、歧义、低置信度和过期场景是否正确拒答或降级 |
| 幻觉率 | 输出事实中无法在证据包中定位的比例 |
| 报告章节完整率 | 必需章节、事实和声明是否齐全 |
| 时效声明准确率 | 过期、缺失和冲突是否被正确标记 |

评测运行输出：

- 运行摘要；
- 总体指标；
- 按问题类型、数据域和策略分组的指标；
- 每个样本的预测、Golden、差异和首错归因；
- 报告章节级差异；
- JSON、JSONL 和 Markdown 导出；
- 代码版本、配置版本、数据版本和模型版本。

建议回归门禁：

- 关键字段严格准确率不得下降；
- 高置信度路径准确率达到约定阈值；
- 幻觉率必须为 0 或接近 0，并对所有无法引用事实判失败；
- 拒答准确率必须单独考核，避免“什么都回答”获得虚高覆盖；
- 人工复核率必须在报告中展示，不能省略。

## 十四、第十二步：系统性能评测

逐字说明：

> 性能评测不是只看总耗时。我们要分别记录身份解析、连接池等待、MySQL、Neo4j、Milvus、LLM 和结果组装耗时，并对简单问答、多跳查询和报告生成分别压测。对外部只读 MySQL 的压测必须限流，并在获得数据源负责人允许后执行，不能直接对未知生产库做高并发压力测试。

场景与初始目标：

| 场景 | 初始目标 |
| --- | ---: |
| 企业基本信息查询 | P95 < 500 ms |
| 股东、融资、风险列表 | P95 < 1 s |
| 最多三跳高置信度路径 | P95 < 3 s |
| 不含 LLM 的报告数据聚合 | P95 < 5 s |
| 包含在线 LLM 的完整报告 | P95 < 30 s，模型耗时单列 |
| 10 并发核心查询 | 错误率 < 1% |
| 数据库连接池 | 无泄漏、无非预期溢出、池等待可观测 |

每次性能运行至少记录：

- P50、P95、P99；
- 吞吐量和并发数；
- 成功率、超时率和错误率；
- MySQL、Neo4j、Milvus、LLM 分段耗时；
- 连接池签出数、等待时间、超时数；
- 缓存冷启动和热命中差异；
- 测试数据版本、代码版本和运行环境。

性能测试分两层：

1. **安全回归层**：使用冻结快照、测试容器或低并发只读数据，持续执行；
2. **受控容量层**：在明确时间窗口和限流参数下连接真实只读库，人工触发，不进入默认 CI。

## 十五、第十三步：实现前端查询与报告工作台

逐字说明：

> 前端不是只放一个聊天框。首版建立独立企业尽调工作台，既支持输入自然语言问题，也支持按企业和数据域直接查询；用户可以在同一页面查看简答、事实表、关系路径、证据来源、数据质量和分段耗时，并可以从当前企业启动完整报告。

建议页面结构：

### 15.1 企业查询页

- 企业搜索：名称、信用代码、股票代码；
- 候选企业选择和身份确认；
- 自然语言问题输入；
- 快捷问题：基本信息、当前股东、融资、风险、知识产权；
- 查询模式：简单问答、关系路径、证据检索；
- 结果标签页：答案、事实、关系图、证据、数据质量、运行明细；
- 低置信度线索默认关闭；
- 缺失、过期、冲突和超时使用明确状态展示。

### 15.2 报告页

- 选择企业和报告章节；
- 创建、取消和重新运行报告任务；
- 展示总体进度和章节进度；
- 查看每个章节的事实、证据和数据质量；
- 下载 JSON 和 Markdown；
- 对失败章节单独重试，不能隐瞒部分失败。

前端 API 必须集中在 `web/src/apis/company_due_diligence_api.js`，页面不能直接拼接普通 HTTP 请求。样式复用 `web/src/assets/css/base.css` 变量，图标优先使用 `lucide-vue-next`。

## 十六、第十四步：实现前端评测工作台

逐字说明：

> 评测必须能够在前端操作和查看，不只保留后端脚本。现有 RAG 评测页面已经有数据集、运行列表、进度、错误筛选和指标展示模式，企业尽调评测可以复用交互经验，但需要独立 API 和独立指标，不能把企业字段准确率硬塞进 RAG 召回指标。

评测工作台包含三个区域：

### 16.1 数据集

- 查看冻结数据集、数据版本、checksum 和人工复核率；
- 按字段问答、关系路径和报告 Golden 筛选；
- 查看样本但隐藏敏感来源连接信息；
- 下载允许导出的 JSON/JSONL。

### 16.2 结果质量运行

- 选择数据集、问题类型、报告模板和查询策略；
- 启动、取消和查看运行进度；
- 展示总体和分类指标；
- 按错误样本、错误类型、数据域和策略筛选；
- 查看预测、Golden、事实差异、路径差异、缺失证据和首错归因；
- 导出 JSON、JSONL 和 Markdown。

### 16.3 性能运行

- 选择场景、并发数、持续时间和是否允许连接真实只读库；
- 对真实库压测增加管理员确认和安全提示；
- 展示 P50/P95/P99、吞吐、错误率和分段耗时；
- 展示连接池等待、占用、超时和泄漏检查；
- 对比多个代码版本、数据版本或策略。

前端建议复用现有 `EvaluationBenchmarks.vue` 和 `RAGEvaluationTab.vue` 的运行状态、分页、错误筛选和进度展示思路，但新建企业尽调领域组件，避免把两个领域耦合在一个超大组件中。

## 十七、完整输入输出链路示例

### 17.1 简单问答

```text
输入企业名称和问题
  → 解析唯一 eid
  → 判断为“当前股东列表”
  → 查询 t_partners_alls 当前记录
  → 解析比例、认缴和实缴 JSON
  → 生成 Fact 与 Source
  → 校验来源、时效和置信度
  → 返回一句简答 + 事实表 + 来源 + 耗时
```

### 17.2 多跳查询

```text
输入两家企业和“有什么关联”
  → 分别解析唯一 eid
  → 生成最多三跳高置信度查询计划
  → Neo4j 返回候选路径
  → 根据每条边的 source_id 回查或校验来源
  → 剔除低置信度和失效关系
  → 返回路径解释 + 节点/边 + 来源 + 置信度
```

### 17.3 完整报告

```text
选择企业和报告章节
  → 创建后台任务并锁定数据版本
  → MySQL、Neo4j、Milvus 并行查询
  → 形成章节数据包
  → 校验事实与来源
  → 生成 JSON 报告
  → LLM 仅根据数据包组织 Markdown
  → 保存报告、checksum 和运行指标
  → 前端展示章节状态并支持下载
```

### 17.4 质量评测

```text
选择人工 Golden 数据集
  → 对每条样本执行真实查询或报告流程
  → 比较字段、关系、路径、来源、拒答和章节
  → 记录首错归因和阶段耗时
  → 聚合总体与分类指标
  → 前端查看并导出结果
```

## 十八、建议实施顺序

```text
Wave 1：只读 MySQL 接入
  ↓
Wave 2：统一契约与企业身份解析
  ↓
Wave 3：结构化查询 / Neo4j 投影 / 文本索引并行
  ↓
Wave 4：问答 API / 报告工作流 / 前端查询报告并行
  ↓
Wave 5：质量评测 / 性能评测 / 前端评测并行
  ↓
Wave 6：端到端回归与发布门禁
```

其中：

- 简单问答最先形成可用闭环，不等待完整报告；
- Neo4j 和 Milvus 都是增强能力，不能阻塞最基础的结构化问答；
- 前端可以在 API 契约冻结后使用 mock 并行开发，但联调验收依赖真实 API；
- AkShare 继续跑公开回归，不参与广东企业主查询 SLA；
- 所有开发和测试复用当前 Docker Compose 服务，不增加重复基础设施。

## 十九、逐步盘点清单

用户可以按下面顺序逐项确认：

- [ ] 接受广东企业 MySQL 作为唯一事实主库。
- [ ] 接受原库只读、不补表、不清洗回写。
- [ ] 确认企业身份以 `eid` 为内部主键。
- [ ] 确认简单问答首版问题类型和返回字段。
- [ ] 确认统一 `Fact / Relation / Path / Evidence / Source` 契约。
- [ ] 确认高、中、低关系置信度规则。
- [ ] 确认 Neo4j 投影范围和最多三跳限制。
- [ ] 确认 Milvus 首版索引的文本类型。
- [ ] 确认完整报告章节和输出格式。
- [ ] 选择首批人工 Golden 企业与问题。
- [ ] 确认质量指标和发布门禁阈值。
- [ ] 确认真实性能压测的安全窗口和并发上限。
- [ ] 确认前端查询、报告和评测页面的信息结构。
- [ ] 按任务依赖波次开始实现。

## 二十、明确非目标

- 不修改或扩展原广东企业数据库表。
- 不把 Neo4j 或 Milvus 变成不可追溯的第二事实库。
- 不让 LLM 执行任意 SQL 或无限制 Cypher。
- 不默认把名称相同视为同一主体或确定关联。
- 不承诺覆盖广东全部企业；当前数据是 924 家特定上市存续企业集合。
- 不在首版自动抓取高风险、需要登录或强反爬网站。
- 不在本轮实现业务代码，也不执行真实数据库压力测试。
