# 企业尽调智能体实现逐字稿

本文是一份可以从头到尾逐项盘点的实施逐字稿。它把《企业尽调智能体》总体方案转换成明确的开发顺序，回答以下问题：当前有什么数据、数据如何只读接入、企业上下文如何建立、自然语言意图如何拆解、内部工具如何编排、不同输出如何动态生成，以及整条链路如何评测。

本文同时记录当前实现和后续边界。截至 2026 年 8 月 11 日，广东企业数据库审计、只读接入、统一事实契约、17 类结构化查询、Neo4j 投影、Milvus/MinIO 文本证据索引、确定性问答、唯一全局共享领域智能体、报告、自动质量/性能评测和两个前端工作台均已实现，自动门禁和管理员部署态 HTTP E2E 已通过；正式发布唯一阻塞项是缺少人工冻结的广东企业 Golden。当前未接入的是在线 LLM 意图/表达节点与交互式关系图。

执行任务清单见仓库根目录的 `tasks/company-due-diligence/README.md`。

## 一、先明确本系统要解决什么问题

逐字说明：

> 我们要建设的不是一组要求用户选择查询模式或预先填写企业主键的数据库页面，而是 Yuxi 智能体体系中的企业尽调领域智能体。用户只需要表达调查要求；系统从问题或可选会话上下文中识别主体，并拆解主题、时间范围、调查深度、输出形式和交付方式，再自动选择结构化查询、图路径、文本证据和报告工具。无须单一企业的全局问题直接进入受控统计，必须依赖企业但缺少唯一主体时才请求补充上下文。
>
> 用户问“当前股东有哪些”，输出就应聚焦股东摘要和列表；用户问“两家公司有什么关系”，输出就应包含关系结论和完整路径；用户说“用报告形式分析近三年的关系和风险”，系统只生成对应专题报告。内部执行工具不同，但全部使用同一套事实、关系、证据、来源和质量契约。

领域智能体必须覆盖以下业务意图：

1. **事实调查**：企业基本信息、股东及出资、产品、融资、处罚、许可、知识产权和财务指标。
2. **关系分析**：共同股东、融资机构网络、历史股东、共同知识产权主体和最多三跳的企业关联路径。
3. **专题调查**：按用户指定主题和时间范围组合事实、路径与证据。
4. **完整尽调**：按标准章节生成可下载的 JSON 和 Markdown 报告。

系统不以“模型回答得像”为成功标准，而以以下结果为成功标准：

- 查到的值与源数据一致；
- 每个重要事实可以定位来源表、来源记录和数据时点；
- 没有数据时明确说没有，不使用模型常识补齐；
- 低置信度名称关系只作为候选线索，不包装成确定事实；
- 同一个问题可以通过冻结数据版本复现；
- 前端按统一 `presentation` 查看摘要、列表、关系路径、专题报告、完整报告、证据、质量指标和性能指标；
- 用户不需要填写内部 `eid`，也不需要理解 MySQL、Neo4j 或 Milvus。

## 二、当前已经有什么数据

### 2.1 广东企业 MySQL：主数据源

逐字说明：

> 当前最有价值的数据不是原来的 30 家公开演示快照，而是现有广东企业 MySQL。它包含 924 家广东上市企业及多域尽调数据，应该作为企业尽调智能体的只读事实主库。我们不修改它，也不向它补表；所有统一、清洗、关系构建和评测都在应用层或可重建投影中完成。

当前已审计的数据资产如下：

| 数据域 | 核心表 | 当前规模 | 当前用途 | 主要限制 |
| --- | --- | ---: | --- | --- |
| 企业主体 | `t_enterprise` | 924 家 | 名称、信用代码、注册资本、法人、状态、区域 | 数据截至 2025 年 12 月，且仅覆盖特定上市存续企业 |
| 上市映射 | `listed_company_gd` | 924 家 | 股票代码与企业主体映射 | 需要和 `eid` 一起固化身份 |

| 公司新闻 | `company_news` | 9,098 条 | 舆情和事件证据 | 企业映射覆盖不足，正文不应无界扫描 |

需要特别说明以下数据质量事实：

- `t_enterprise.eid` 是当前最稳定的企业内部主键。
- 924 家企业均有企业名称、统一社会信用代码、注册资本、法人、状态和区域代码。
- 当前股东 7,305 条，历史股东 5,866 条；只有部分股东可以通过稳定 ID 连接到其他企业。
- 已识别 232 个关联多家企业的共同股东键，其中 121 个有稳定 ID，111 个只能依赖名称。
- 自然人姓名、同名产品和单一新闻名称命中只能作为低置信度候选。
- 财务、新闻和 `t_enterprise_equity` 不能直接按当前字段完整映射到 924 家企业，首版必须明确覆盖范围。

完整审计依据保存在本地开发记录 `docs/vibe/2026-08-10-guangdong-enterprise-data-audit.md`；`docs/vibe` 默认不提交，正式数据结论已在本节完整列出。

逐字说明：

> AkShare 不再与广东企业数据库并列为双主库。现有 30 家公开上市公司快照继续保留，因为它无敏感连接依赖、可以公开复现，适合做开发回归和演示；后续也可以用于公告、最新公开披露和主库时效核验，但不能静默覆盖 MySQL 中的事实。

逐字说明：

> 本项目已经通过 Docker Compose 管理 PostgreSQL、Redis、MinIO、Milvus、Neo4j、API、worker 和 web。尽调系统只增加业务接入和业务 API，不新增一套 PostgreSQL、MinIO、Redis、Neo4j、Milvus 或 MySQL 容器，也不要求重复拉取已有镜像。外部广东 MySQL 通过环境变量只读接入。

## 三、第一步：只读接入广东企业 MySQL

逐字说明：

> 第一项开发任务不是写问答提示词，而是建立一个健康、限流、可观测的只读 MySQL 接入层。所有后续 SQL 查询、图谱投影和评测快照都必须经过这一层。应用启动时只验证连接和必要表，不执行建表、迁移、更新或自动修复。

### 3.1 配置读取

- 从本地不提交的 `.env` 或容器环境读取 `MYSQL_URL`；仓库中的 `.env.template` 仅保存脱敏占位格式。
- 当前 `f"mysql+aiomysql://...:{quote('password')}@..."` 格式通过受限 AST 安全解析，只允许单个 `quote('password')` 插值，不执行 `eval`。
- 不把完整 DSN 写入日志、异常、接口响应、测试快照或文档。
- 如果现有 `.env` 使用 Python 表达式而不是标准 DSN，应在配置解析层显式处理或先改成标准环境变量格式，不能通过 `eval` 执行。
- 健康检查只返回“已配置、可连接、延迟、连接池状态、必要表是否存在”，不返回主机、用户名和密码。

### 3.2 健康连接池

首版连接池基线：

```text
pool_size = 2
max_overflow = 0
pool_pre_ping = true
pool_recycle = 300s
pool_timeout = 5s
connect_timeout = 8s
statement_timeout = 5~10s
session = READ ONLY
```

生产参数可以通过性能评测调整，但以下约束不变：

- 不允许无限连接和非预期溢出；
- 每条大表查询必须带企业键、时间范围、索引条件和分页上限；
- 超时应显式失败并记录数据源阶段耗时，不能无限重试；
- 连接归还、池等待和超时需要形成指标；
- 禁止执行 `INSERT`、`UPDATE`、`DELETE`、`CREATE`、`ALTER`、`DROP`、`TRUNCATE`。

### 3.3 Repository 边界

只读 Repository 应按业务域组织，而不是把任意 SQL 暴露给 LLM：

- `EnterpriseRepository`：企业身份和基本信息；
- `ShareholderRepository`：当前/历史股东及出资；
- `ProductRepository`：产品；
- `FinanceRepository`：融资；
- `RiskRepository`：处罚、异常和许可；
- `IntellectualPropertyRepository`：专利、商标和著作权；
- `FinancialMetricRepository`：财务指标；
- `NewsRepository`：新闻元数据和允许读取的文本字段。

每个方法都应该是明确的业务查询，例如 `list_current_shareholders(eid, limit)`，而不是 `execute_sql(sql)`。

### 3.4 这一步的输入输出

输入：

```json
{
  "operation": "get_enterprise",
  "eid": "内部企业标识"
}
```

输出：

```json
{
  "record": {},
  "source_table": "t_enterprise",
  "source_key": "脱敏后的稳定记录标识",
  "data_as_of": "2025-12-01",
  "local_updated_at": "2025-12-08",
  "latency_ms": 0
}
```

验收重点：通过集成测试证明查询成功、写操作被拒绝、连接池无泄漏、超时能回收连接、日志不包含完整 DSN。

## 四、第二步：建立企业身份解析

逐字说明：

> 普通用户通常只会在问题中提供企业全称、股票代码、信用代码或“这家企业”这样的会话指代，而不会知道内部 `eid`。`question` 是唯一必填业务输入，企业搜索和已确认上下文只是可选辅助。企业依赖问题必须先把用户提及解析成唯一企业身份；全局白名单统计不要求单一企业。解析失败时返回候选或 `needs_context`，不能因为名称相似就自动选中一家企业。

解析优先级：

1. 问题或可选上下文中的统一社会信用代码精确匹配；
2. 问题或可选上下文中的股票代码精确匹配；
3. 问题或可选上下文中的企业标准全称精确匹配；
4. 已确认企业上下文中的 `eid` 精确复用；
5. 规范化名称精确匹配；
6. 模糊名称只返回候选，不自动进入事实查询。

当前统一问答输入：

```json
{
  "question": "广东某某股份有限公司的股东有哪些？",
  "company_ref": null
}
```

领域智能体不要求普通用户直接构造 `company_ref`。系统先从问题中提取企业法律全称、股票代码和信用代码；`company_ref` 仅用于继承已经确认的会话上下文。没有企业提及时，固定白名单的企业目录覆盖和共同股东问题返回 `global_scope`，其余企业依赖问题返回 `needs_context`。`eid` 只在解析结果和后续工具参数中使用。

统一解析结果：

```json
{
  "status": "resolved",
  "entity": {
    "eid": "稳定内部标识",
    "name": "标准企业名称",
    "unified_social_credit_code": "脱敏展示值或按权限返回",
    "stock_code": "股票代码"
  },
  "match_method": "stock_code_exact",
  "confidence": "high",
  "candidates": []
}
```

如果存在多个候选，返回 `status=ambiguous`，前端要求用户选择；如果明确提及的主体不存在，返回 `status=not_found`；如果问题需要企业但没有可解析主体，返回 `scope_status=needs_context`。这些状态都不能继续生成确定性企业事实答案。

## 五、第三步：冻结领域智能体意图与输出契约

逐字说明：

> 工作台问答、主智能体调用、报告按钮和评测不能各自设计一套输入输出。我们先定义企业上下文、内部意图、统一事实和动态展示契约，再让 SQL、Neo4j、Milvus、报告服务和 LLM 都围绕这套契约工作。

### 5.1 用户输入与内部意图

用户可见输入保持简单：

```json
{
  "question": "请用报告形式分析广东某某股份有限公司近三年的关系和风险",
  "company_ref": null
}
```

领域智能体归一后的内部意图：

```json
{
  "entities": [
    {"eid": "系统解析结果", "role": "primary_company"}
  ],
  "intent": {
    "topics": ["relations", "risks"],
    "presentation": "topic_report",
    "delivery": "async_task",
    "time_scope": {"type": "recent_years", "years": 3},
    "depth": "detailed",
    "evidence_required": true
  },
  "constraints": {
    "hop_limit": 3,
    "include_low_confidence": false
  }
}
```

`StructuredQuery`、`GraphPath` 和 `EvidenceSearch` 是内部工具，不是用户模式。统一 `/investigations` 入口负责生成意图和工具计划；旧 `company_ref + question + mode` 契约继续兼容，但 `question` 已是唯一必填业务字段，`company_ref` 不能作为页面进入或评测启动条件。

### 5.2 统一响应

```json
{
  "request_id": "请求标识",
  "status": "complete",
  "understood_request": {
    "topics": ["shareholders"],
    "presentation": "summary_with_list",
    "delivery": "sync"
  },
  "entities": [],
  "summary": "面向用户的直接回答",
  "findings": [],
  "facts": [],
  "relations": [],
  "paths": [],
  "evidence": [],
  "sources": [],
  "data_quality": {
    "source_status": "available",
    "missing_fields": [],
    "stale_fields": [],
    "conflicts": [],
    "warnings": [],
    "minimum_confidence": "high"
  },
  "latency": {
    "resolution_ms": 0,
    "mysql_ms": 0,
    "neo4j_ms": 0,
    "milvus_ms": 0,
    "llm_ms": 0,
    "assembly_ms": 0,
    "total_ms": 0
  },
  "presentation": {
    "type": "summary_with_list",
    "components": ["summary", "shareholder_table", "sources"]
  },
  "task": null
}
```

`understood_request` 用于展示系统如何理解用户要求；`presentation` 用于通知前端动态渲染，不是让用户预先选择；`task` 只在专题报告、完整报告等异步任务中返回。

每个 `Fact` 至少包含：

```json
{
  "fact_id": "事实标识",
  "subject_id": "企业或关系主体标识",
  "fact_type": "registered_capital",
  "normalized_value": "规范化值",
  "display_value": "面向用户的值",
  "unit": "CNY",
  "effective_date": null,
  "confidence": "high",
  "source_id": "来源标识"
}
```

每个 `Source` 至少包含：

```json
{
  "source_id": "来源标识",
  "source_system": "guangdong_enterprise_mysql",
  "table": "t_enterprise",
  "record_key": "可追溯但不泄露凭据的记录键",
  "business_date": "数据业务日期",
  "queried_at": "本次查询时间"
}
```

统一契约必须显式表达：无数据、字段缺失、数据过期、来源冲突、映射置信度不足、查询阶段超时，以及输出是否覆盖了用户要求的主题和形式。

## 六、第四步：先实现结构化工具与基础意图闭环

逐字说明：

> 首版不能等完整报告和图谱全部完成后才可用。我们先实现结构化查询工具和确定性基础意图，让“股东有哪些”“注册资本是多少”等明确问题走最短链路。LLM 后续只负责补充复杂意图理解和表达，不生成数据库里没有的值。

> 实施状态（2026 年 8 月 10 日）：底层 17 类白名单结构化查询已完成，入口为 `POST /api/company-due-diligence/structured-query`；自然语言意图识别和答案组织由后续问答任务实现。

### 6.1 基础意图完整链路

```text
企业上下文和用户问题
  → 复用或解析唯一企业
  → 业务主题与 presentation 识别
  → 参数抽取与校验
  → 只读 MySQL Repository
  → 事实规范化
  → 来源与时效校验
  → 直接摘要与列表组织
  → 统一响应和动态展示
```

### 6.2 首版业务主题

| 问题类型 | 示例 | 主查询源 |
| --- | --- | --- |
| 企业基本信息 | 注册资本、法人、状态、成立时间、经营范围 | `t_enterprise` |
| 当前股东 | 当前股东有哪些、持股比例多少 | `t_partners_alls` |
| 历史股东 | 历史股东和退出时间 | `t_partners_alls` |
| 股东出资 | 认缴、实缴、出资比例和出资明细 | `t_partners_alls` |
| 产品 | 有哪些产品、产品描述和渠道 | `t_company_products` |
| 融资 | 融资轮次、金额、时间、投资机构 | `t_company_finance` |
| 风险 | 行政处罚、环保处罚、经营异常 | 风险相关表 |
| 许可 | 许可数量、类型和有效期 | `t_license_info` |
| 知识产权 | 专利、商标、著作权数量和列表 | 知识产权相关表 |
| 财务 | 指标时间序列和覆盖范围 | 财务指标表 |

### 6.3 基础意图示例

输入：

```json
{
  "company_context": "已确认企业",
  "message": "这家公司的注册资本是多少？"
}
```

输出逻辑：

1. 股票代码精确解析为 `eid`；
2. 从 `t_enterprise` 查询注册资本；
3. 规范化金额和币种；
4. 返回一句简答；
5. 同时返回对应 `Fact`、`Source`、数据时点和 MySQL 耗时；
6. 如果字段缺失，回答“当前数据源未提供”，不能推测。

回答文本示例：

```text
根据企业主表记录，该企业注册资本为〔规范化金额〕。该数据的业务时点为〔日期〕；如需当前工商状态，应进一步通过公开披露进行时效核验。
```

### 6.4 调查中的拒答规则

以下情况必须拒绝或降级：

- 企业身份存在多个候选；
- 请求字段不在允许的数据域；
- 只有低置信度名称关系，却要求确定性控制关系；
- 查询超时或关键来源不可用；
- 数据已明显过期且问题要求“当前”“最新”；
- 多个来源冲突且没有明确优先规则。

拒答也必须返回原因、已查来源和下一步建议，不能只返回“无法回答”。

## 七、第五步：构建 Neo4j 可重建关系投影

逐字说明：

> MySQL 适合查精确字段，但共同股东、融资机构网络和多跳关联路径不应该在每次请求中临时拼接大量 SQL。我们从 MySQL 生成带版本的 Neo4j 投影。Neo4j 只负责关系遍历，不成为第二事实主库；任何节点和关系都必须能追溯到 MySQL 来源并能够全量重建。

> 实施状态（2026 年 8 月 10 日）：版本化投影、checksum 快照、幂等写入、统计校验、Tasker 管理接口和最多三跳内部查询已完成；默认严格查询只使用高置信度边。

### 7.1 首版图谱对象

节点：

- `Company`：以 `eid` 为稳定键；
- `Shareholder`：稳定 `stock_id` 优先，标准化名称为候选键；
- `FinancingEvent`：企业、轮次、时间和来源记录组合键；
- `Investor`：投资人 ID 优先；
- `Patent`、`Trademark`、`Copyright`：使用稳定业务号；
- `Punishment`、`License`：使用来源记录稳定键；
- `Regulator`：标准化机关名称。

关系：

- `HOLDS`：股东持有企业；
- `RECEIVED_FINANCING`：企业获得融资；
- `INVESTED_IN`：投资人参与融资；
- `OWNS_PATENT`、`OWNS_TRADEMARK`、`OWNS_COPYRIGHT`；
- `PUNISHED_BY`、`LICENSED_BY`。

每条关系至少保存：来源表、来源记录键、当前/历史状态、有效日期、投影版本和置信度。

### 7.2 置信度规则

- **高置信度**：`eid`、信用代码、股票代码、稳定股东 ID、融资投资人 ID、专利申请号等稳定键。
- **中置信度**：标准企业全称一致，并且区域、法人、信用代码片段或其他辅助字段一致。
- **低置信度**：自然人姓名、产品名称、新闻中的单字段名称命中。

默认多跳事实答案只使用高置信度关系。中低置信度关系可以在“线索模式”返回，但必须标明候选性质。

### 7.3 投影过程

```text
读取 MySQL 只读批次
  → 规范化企业与关系键
  → 生成投影快照和 checksum
  → 校验节点、边、孤儿和重复关系
  → 幂等写入 Neo4j 指定版本
  → 记录投影统计
  → 切换当前可查询版本
```

不允许边查边把 LLM 推测关系写进图谱。`RELATED_TO` 不是原始事实，只能在查询时根据基础关系路径派生。

## 八、第六步：实现多跳关系查询

逐字说明：

> 多跳问题必须先解析起点企业、目标企业、允许的关系类型、最大跳数和置信度要求，再执行受控 Cypher。LLM 不直接生成无限制 Cypher；系统使用参数化模板或经过校验的查询计划，最大跳数首版限制为三跳。

首版多跳问题：

1. 企业 → 当前/历史股东 → 其他企业；
2. 企业 → 融资事件 → 投资机构 → 其他被投企业；
3. 企业 → 知识产权 → 共同权利主体或关联企业；
4. 企业 → 处罚/许可机关 → 同类企业；
5. 两家企业之间的最短高置信度路径；
6. 某股东或投资机构关联的企业网络。

多跳输出不能只有自然语言，至少还要返回：

```json
{
  "path_id": "路径标识",
  "hop_count": 2,
  "nodes": [],
  "edges": [],
  "confidence": "high",
  "derivation": "共同股东路径",
  "source_ids": []
}
```

回答时应明确区分：

- “存在一条由稳定股东 ID 支撑的高置信度路径”；
- “仅发现同名主体候选，不能确认实际关联”；
- “在当前最多三跳、当前投影版本中未找到路径”。

## 九、第七步：接入文本证据检索

逐字说明：

> 结构化字段可以回答“有什么”，但新闻、处罚原因、许可内容和专利摘要需要文本证据。我们复用现有 Milvus 和 MinIO，不新增向量数据库或对象存储。文本索引从 MySQL 只读抽取，可以随时删除并重建。

首版建议索引：

- 新闻标题、摘要和允许读取的正文；
- 行政处罚事实、依据、决定和处罚机关；
- 环保处罚内容；
- 行政许可事项和许可内容；
- 专利摘要；
- 产品描述。

每个文本块元数据至少包含：

```json
{
  "document_id": "稳定文档标识",
  "eid": "企业标识",
  "source_table": "来源表",
  "source_record_key": "来源记录键",
  "document_type": "news",
  "published_at": "业务日期",
  "projection_version": "索引版本",
  "checksum": "内容校验值"
}
```

检索流程：

```text
企业身份和问题
  → 先按 eid、文档类型和日期过滤
  → 在过滤结果中向量召回
  → 必要时重排
  → 返回原文片段和元数据
  → 事实核验后进入答案或报告
```

Milvus 检索结果只是证据候选。金额、日期、处罚状态和企业身份等结构化事实仍以 MySQL 为准。

> 实施状态（2026 年 8 月 10 日）：六类文本来源的只读游标抽取、清洗分块、SQLite checksum 快照、版本化 Milvus collection、MinIO 归档与原子当前指针、Tasker 管理接口和企业/类型/日期过滤查询已完成。新闻只接受标准企业全称精确映射，索引失败不切换当前版本，查询结果强制校验 `eid`、`source_id` 和投影版本。

## 十、第八步：用 LangGraph 编排领域智能体

逐字说明：

> 当结构化查询、图谱和文本检索都具备后，LangGraph 的职责是承载 `CompanyDueDiligenceAgent`：维护企业上下文、拆解业务意图、选择工具、控制步骤、校验 Claim Ledger 并路由输出，而不是充当事实数据库。简单字段问题只走短链路；关系问题走图谱链路；需要解释的风险问题再增加文本证据；专题或完整报告进入异步报告工具。

建议节点：

```text
load_company_context
  → resolve_referenced_entities
  → understand_investigation_intent
  → validate_intent_schema
  → build_tool_plan
  → query_mysql / query_neo4j / retrieve_evidence
  → build_claim_ledger
  → validate_claims
  → compose_response_or_create_report
  → attach_sources
  → select_presentation
  → finalize_metrics
```

路由原则：

- 基本信息、股东列表、融资列表、风险统计等意图走 MySQL；
- 共同股东、最短路径和投资网络意图走 Neo4j；
- 新闻解释、处罚原因、许可内容和专利摘要意图走 Milvus，并回查 MySQL 元数据；
- 一个问题可以并行查询多个源，但最终只输出已验证的事实；
- 报告自然语言意图和报告按钮必须归一到同一个 `ReportGenerationTool`；
- LLM 输出必须通过实体、事实、数值、日期、路径和来源引用检查，无法匹配 `source_id` 的企业事实不得进入最终答案；
- 后置校验失败时回退模板输出，不以流畅度覆盖正确结构化结果。

短问题应同步响应；耗时较长的专题报告、完整报告和评测使用后台任务与 SSE/轮询进度，复用现有 Tasker 和前端任务模式。

> 实施状态（2026 年 8 月 11 日）：`POST /api/company-due-diligence/investigations` 已完成企业上下文解析、确定性意图、白名单计划、短链路工具抑制、最多三跳图查询、企业过滤证据检索、报告任务路由、Claim Ledger 和动态 `presentation`；`/query` 保持兼容，管理员部署态 HTTP E2E 已通过。

## 十一、第九步：生成完整尽调报告

逐字说明：

> 报告不是把一个长提示词交给模型，也不是独立于问答之外的第二套产品。用户可以在自然语言中要求专题或完整报告，也可以点击报告快捷按钮；两个入口都生成统一意图，再由 `CompanyDueDiligenceAgent` 调用同一个报告工具。报告服务先确定企业身份和数据版本，再并行拉取章节事实、关系路径和文本证据，最后才由模板和 LLM 生成摘要。

> 实施状态（2026 年 8 月 10 日）：十二章节并行工作流、版本锁定、章节状态、Tasker 进度/取消、单章节重试、MinIO JSON/Markdown/record 产物和下载 checksum 校验已完成；单章节失败保留其他成功章节并将整体标记为 `partial`。

### 11.1 报告意图

```json
{
  "entities": [{"eid": "系统已确认企业", "role": "primary_company"}],
  "intent": {
    "topics": ["relations", "risks"],
    "presentation": "topic_report",
    "delivery": "async_task",
    "time_scope": {"type": "recent_years", "years": 3},
    "depth": "detailed",
    "evidence_required": true
  }
}
```

点击“生成完整尽调报告”时，前端只需构造 `topics=["full_due_diligence"]`、`presentation="full_report"` 的标准意图。当前独立报告 API 可作为兼容适配层，但不能拥有不同的企业解析和来源规则。

### 11.2 报告章节

1. 企业身份确认；
2. 工商基本信息；
3. 股权结构与出资；
4. 多跳关联与关联线索；
5. 产品与业务；
6. 融资历程；
7. 财务表现；
8. 经营合规与许可；
9. 知识产权与创新；
10. 新闻舆情；
11. 关键风险和待核验事项；
12. 数据质量、来源和时效声明。

### 11.3 报告执行链路

```text
接收自然语言报告意图或报告按钮意图
  → 归一成统一内部意图
  → 锁定企业身份和数据版本
  → 并行查询各章节
  → 汇总事实、路径和证据
  → 章节数据质量检查
  → 生成结构化报告 JSON
  → 生成 Markdown 摘要
  → 保存文件产物与 checksum
  → 统一响应返回 task、presentation 和下载信息
```

报告章节状态至少支持：

- `complete`：数据和来源完整；
- `partial`：有结果但字段或覆盖不完整；
- `no_data`：当前来源没有记录；
- `stale`：数据时点不能支撑当前性结论；
- `conflicted`：多个来源存在未解决冲突；
- `failed`：查询或生成失败。

报告不能因为某个非关键章节失败而整体伪装成功；前端应看到章节状态和失败原因。

## 十二、第十步：冻结快照与人工 Golden

逐字说明：

> 没有冻结数据和人工答案，就无法判断改动后到底变好还是变差。我们从 MySQL 只读导出一批经过脱敏的评测快照，并由人工核对简单问题、多跳路径和报告章节。评测不能继续用程序自己生成答案再评价程序自己。

> 实施状态（2026 年 8 月 10 日）：数据集版本、checksum、业务时点、来源类别和 `review_status` 契约已完成，并提供 `source_derived_unreviewed` 开发烟测数据；`human_verified` 强制记录 `reviewed_by`、`reviewed_at` 和 `reviewer_note`，冻结脚本负责校验并原子写入 checksum。首批人工 Golden 仍需数据负责人和业务复核人员共同完成。

Golden 至少包含三类：

1. **字段问答集**：企业基本信息、股东、出资、产品、融资、风险和知识产权；
2. **关系路径集**：共同股东、投资机构网络、最短路径和无路径问题；
3. **报告 Golden**：选定企业的章节事实、必要来源、缺失声明和人工风险摘要。

每条样本至少保存：

```json
{
  "case_id": "样本标识",
  "dataset_version": "数据集版本",
  "question_type": "registered_capital",
  "input": {},
  "expected_facts": [],
  "expected_paths": [],
  "required_sources": [],
  "expected_refusal": false,
  "review_status": "human_verified",
  "reviewed_at": "人工复核日期"
}
```

冻结产物需要 checksum、生成时间、源数据业务时点、脱敏说明和人工复核状态。评测数据文件不保存数据库密码或完整连接信息。

## 十三、第十一步：结果质量评测

逐字说明：

> 质量评测要覆盖从用户输入到最终输出的整条链路，同时评企业上下文、意图对象、工具计划、事实、路径、来源、拒答、报告章节和 `presentation`。自然语言相似度只能作为辅助指标，不能代替字段、路径和输入输出一致性的严格比较。

> 实施状态（2026 年 8 月 11 日）：质量运行服务、Tasker 进度/取消、逐题预测与 Golden 差异、分组指标、首错归因和 JSON/JSONL/Markdown 导出已完成。系统可从全局只读数据目录自动生成字段、关系、证据、报告和拒答/歧义五类 `source_derived` 样本，并记录数据版本、来源、checksum、总体分母、抽样策略与跳过原因。开发烟测自动通过，但没有人工 Golden 时 `regression_gate.eligible=false`，不得宣称正式质量门禁通过。

首版核心指标：

| 指标 | 计算重点 |
| --- | --- |
| 字段严格准确率 | 值、单位、日期和企业身份全部正确 |
| 企业解析准确率 | 当前企业和问题中其他企业是否解析成正确主体 |
| 意图理解准确率 | 主题、时间、深度、展示和交付方式是否与人工标注一致 |
| 工具计划准确率 | 必要工具是否调用、无关工具是否避免、参数是否满足约束 |
| 关系严格准确率 | 起点、终点、关系类型、方向和属性正确 |
| 多跳路径准确率 | 节点序列、边序列、方向和跳数与 Golden 一致 |
| 证据覆盖率 | 每个必需事实都存在有效 `source_id` |
| 拒答准确率 | 无数据、歧义、低置信度和过期场景是否正确拒答或降级 |
| 幻觉率 | 输出事实中无法在证据包中定位的比例 |
| 报告章节完整率 | 必需章节、事实和声明是否齐全 |
| 时效声明准确率 | 过期、缺失和冲突是否被正确标记 |
| 输入输出一致率 | 用户要求的主题和形式是否被覆盖，是否加入无关章节 |
| presentation 匹配率 | 摘要、列表、关系结果、专题报告或完整报告是否选择正确 |

评测运行输出：

- 运行摘要；
- 总体指标；
- 按问题类型、数据域和策略分组的指标；
- 每个样本的预测、Golden、差异和首错归因；
- 报告章节级差异；
- JSON、JSONL 和 Markdown 导出；
- 代码版本、配置版本、数据版本和模型版本。

建议回归门禁：

- 关键字段严格准确率不得下降；
- 高置信度路径准确率达到约定阈值；
- 幻觉率必须为 0 或接近 0，并对所有无法引用事实判失败；
- 拒答准确率必须单独考核，避免“什么都回答”获得虚高覆盖；
- 人工复核率必须在报告中展示，不能省略。
- 输出必须覆盖用户要求的主题，且无关内容率不得超过人工确认阈值。
- LLM 接入后必须单独报告意图、Claim Ledger 一致性、来源引用和模板回退指标。

## 十四、第十二步：系统性能评测

逐字说明：

> 性能评测不是只看总耗时。我们要分别记录身份解析、连接池等待、MySQL、Neo4j、Milvus、LLM 和结果组装耗时，并对简单问答、多跳查询和报告生成分别压测。对外部只读 MySQL 的压测必须限流，并在获得数据源负责人允许后执行，不能直接对未知生产库做高并发压力测试。

> 实施状态（2026 年 8 月 11 日）：六类场景、进程内异步 runner、安全模式、受控真实库确认、Tasker 运行/取消和全局自动选样已完成。报告包含 P50/P95/P99、吞吐、错误/超时/取消率、接口、意图、工具链、数据源请求、Tasker 排队等待、worker、CPU/RSS 和连接池指标；任务载荷与最终报告均不保存企业引用明细。当前报告不调用在线 LLM，因此 `report_with_llm` 只返回 `skipped/unavailable`，不复用无 LLM 结果冒充。

场景与初始目标：

| 场景 | 初始目标 |
| --- | ---: |
| 企业基本信息查询 | P95 < 500 ms |
| 股东、融资、风险列表 | P95 < 1 s |
| 最多三跳高置信度路径 | P95 < 3 s |
| 不含 LLM 的报告数据聚合 | P95 < 5 s |
| 包含在线 LLM 的完整报告 | P95 < 30 s，模型耗时单列 |
| 10 并发核心查询 | 错误率 < 1% |
| 数据库连接池 | 无泄漏、无非预期溢出、池等待可观测 |

每次性能运行至少记录：

- P50、P95、P99；
- 吞吐量和并发数；
- 成功率、超时率和错误率；
- MySQL、Neo4j、Milvus、LLM 分段耗时；
- 连接池签出数、等待时间、超时数；
- 缓存冷启动和热命中差异；
- 测试数据版本、代码版本和运行环境。

性能测试分两层：

1. **安全回归层**：使用冻结快照、测试容器或低并发只读数据，持续执行；
2. **受控容量层**：在明确时间窗口和限流参数下连接真实只读库，人工触发，不进入默认 CI。

## 十七、完整输入输出链路示例

### 17.1 股东调查

```text
输入“广东某某股份有限公司的股东有哪些”
  → 从问题提取企业全称并解析唯一 eid
  → 解析 topics=shareholders、presentation=summary_with_list
  → 规划 StructuredQueryTool
  → 查询 t_partners_alls 当前记录
  → 解析比例、认缴和实缴 JSON
  → 生成 Claim、Fact 与 Source
  → 校验来源、时效、置信度和输入输出一致性
  → 返回股东摘要 + 股东列表 + 来源 + 耗时
```

### 17.2 企业关系调查

```text
输入两家企业和“有什么关联”
  → 分别解析唯一 eid
  → 解析 topics=relations、presentation=relation_result
  → 规划 GraphPathTool
  → 生成最多三跳高置信度查询计划
  → Neo4j 返回候选路径
  → 根据每条边的 source_id 回查或校验来源
  → 剔除低置信度和失效关系
  → 返回路径解释 + 节点/边 + 来源 + 置信度
```

### 17.3 关系与风险专题报告

```text
输入“用报告形式分析近三年的关系和风险”
  → 解析 topics=relations,risks、time_scope=recent_3_years
  → 选择 presentation=topic_report、delivery=async_task
  → 规划 GraphPathTool、StructuredQueryTool、EvidenceSearchTool、ReportGenerationTool
  → 创建后台任务并锁定数据版本
  → MySQL、Neo4j、Milvus 并行查询
  → 形成关系和风险 Claim Ledger
  → 校验事实、路径、来源和专题范围
  → 生成专题 JSON 报告
  → 模板生成基础 Markdown；启用在线 LLM 后只能基于数据包组织文本
  → 保存报告、checksum 和运行指标
  → 前端展示章节状态并支持下载
```

点击“生成完整尽调报告”使用相同链路，只是标准意图中的 `topics=full_due_diligence`、`presentation=full_report`。

### 17.4 全链路质量评测

```text
选择数据版本并启动自动评测，无需填写企业名称
  → 从全局目录生成 source_derived 字段、关系、证据、报告和拒答样本
  → 记录总体分母、抽样策略、来源、checksum 和跳过原因
  → 对每条样本执行真实领域智能体
  → 比较实体、意图、工具计划、字段、关系、路径、来源和 presentation
  → 记录首错归因和阶段耗时
  → 聚合总体与分类指标
  → 与 human_verified 人工 Golden 分组展示
  → 前端查看并导出结果
```

其中：

- 当前 Wave 1～Wave 8 已形成全局共享领域智能体闭环；
- 明确事实调查继续保持短链路，不等待完整报告；

- 所有开发和测试复用当前 Docker Compose 服务，不增加重复基础设施。

### Wave 6 发布门禁

使用本地不提交的 `.env` 启动 Compose 后，执行 `scripts/company_due_diligence/run_release_gate.sh`。如果本机需要端口覆盖，通过 `COMPANY_DD_COMPOSE_OVERRIDE` 指定额外 Compose 文件。脚本串联后端回归、管理员 E2E、AkShare 120 题基线、敏感信息审计、质量烟测、安全性能基线、发布报告和前端验证；管理员 E2E 由临时 `api` 容器读取当前 `.env`，AkShare 与最终报告均写入被忽略的 `saves/company_due_diligence/release/`，不会污染源码工作区。正式发布或 CI 使用 `run_release_gate.sh --enforce`，任何自动失败或人工阻塞都会返回非零。

自动门禁与正式发布状态必须分开：固定开发烟测只验证评测链路，正式门禁自动选择最新的已冻结、含 `human_verified` 样本的广东企业数据集，也可通过 `COMPANY_DD_HUMAN_QUALITY_DATASET` 显式指定。`2026-08-11` 自动门禁和管理员部署态 HTTP E2E 已通过，当前唯一阻塞项是缺少正式 Golden。在线 LLM 报告未启用时必须标记 `unavailable`，但不额外阻塞当前模板报告发布口径。

### Wave 7 领域智能体升级（已完成自动验收）

1. 冻结企业上下文、内部意图、Claim Ledger 和统一响应 schema。

3. 用规则和报告按钮覆盖确定性意图；受约束 LLM 作为后续可选节点。
4. 增加意图 schema 校验、Claim 后置校验和模板回退。
5. 将前端改为企业上下文 + 单一调查输入框 + 动态 `presentation`。
6. 增加意图、工具计划和输入输出一致性 Golden 与发布门禁。

### Wave 8 全局共享与自动评测（已完成自动验收）

1. 启动时幂等注册唯一 slug 为 `company-due-diligence` 的全局共享 Agent，仅挂载受控 `investigate_company` 工具。
2. 将 `question` 固化为唯一必填业务输入，从问题自动提取企业全称、股票代码和信用代码。

5. 性能评测自动选样并聚合接口、意图、工具链、数据源、Tasker、worker 和连接池阶段指标，不保存企业引用明细。
6. 前端查询、质量评测和性能评测均取消企业必填阻断，完成单元、真实集成和管理员 HTTP E2E 回归。
